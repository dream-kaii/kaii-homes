## 为什么哈希是性价比最高的一类 {/* s1 */}

哈希题在 Hot 100 里占的篇幅不小，但核心思想只有一句话：

> **用空间换时间，把查找从 O(n) 降到 O(1)。**

这么一句话能撑起一整类题，是因为它把「找东西」的成本结构彻底改了。暴力解法里，每次「看看某个值在不在」都要线性扫一遍；哈希表把这次扫描变成一次计算 —— 算哈希、定位桶、比一次。代价是你得提前把数据放进去，也就是**多花 O(n) 的空间**。

这个交换在面试里几乎总是划算的。所以哈希题的难点从来不在写代码：**认出来了，代码基本是机械的；认不出来，你会顺着「两层循环」的直觉写下去，写出一个能过样例但复杂度不达标的解，然后卡在那儿优化不动。**

### 这个系列的定位

这是我算法路线里的第 2 步（第 1 步「按题型规划刷题顺序」还没写成文章）。结论先放这儿：**刷题要按题型集中攻，不要按题号顺序刷，哈希是最好的第一个专题** —— 信号最好认、模板最固定、复现率最高。

同系列的 [滑动窗口题型的统一思路](/writing/sliding-window/) 和 [链表题的指针套路整理](/writing/linked-list-patterns/) 用的是同一套结构：**先讲识别信号，再讲套路，最后讲代价。**

## 识别信号：这四个字眼是条件反射 {/* s2 */}

题目里出现下面这几类表述，基本可以直接往哈希上想。不是「可能」，是「先试这个」。

| 信号 | 典型问法 | 哈希里存什么 |
| --- | --- | --- |
| 是否存在 / 有没有重复 | 「是否存在两个数…」「有没有重复元素」 | 出现过的值（set）或 值 → 下标 |
| 配对 / 互补 | 「两数之和等于 target」「配对成…」 | 互补值 → 位置 |
| 计数 | 「出现次数」「频率」「最多/最少出现」 | 值 → 计数 |
| 分组 | 「互为变位词」「归为同一类」 | 规范化后的 key → 属于该组的元素列表 |

**「是否存在」**：哈希表的定义就是「常数时间判断成员是否在集合里」，所以只要答案是「在不在」，它就是天然匹配的工具。要求「在哪儿」就把值映射到下标，要求「几个」就映射到计数。
**「配对」**：这是最容易忽略的一类。配对题的特点是**两个元素之间存在一个确定的关系式**，比如 `a + b == target`。关系式一旦确定，就知道了其中一个，另一个就唯一确定：`a` 定了，`b` 只能是 `target - a`。于是遍历到 `a` 时，问题从「找出所有可能的 `b`」缩小成了「查一下 `target - a` 在不在」，**搜索空间从「整个数组」压缩到了「一个确定的值」。**

**「计数」和「分组」**：计数的本质是「同一个值出现多次」，需要把相同的值聚到一起累加，正好是哈希的键去重能力。分组更进一步 —— 你得先把「属于同一组」这个关系抽象成一个 key，再用它归并；**分组题的难度几乎全在 key 的设计上。**

> **提示**
>
> 还有个反向信号：**题目要求「O(n) 时间内解决」** —— 这句话在暗示你现有解法里有一层循环可以被「查表」替掉。看到这个约束，先想想哪一层循环在做重复的查找。

## 题一：两数之和 {/* s3 */}

> 给定一个整数数组 `nums` 和一个整数目标值 `target`，在该数组中找出和为目标值的两个整数，返回它们的数组下标。

### 暴力解法浪费在哪

```python
def two_sum_brute(nums: list[int], target: int) -> list[int]:
    """暴力：两两配对。O(n^2)。"""
    n = len(nums)
    for i in range(n):
        for j in range(i + 1, n):
            if nums[i] + nums[j] == target:
                return [i, j]
    return []
```

内层循环在做什么：固定 `i` 之后，它把**整个数组扫了一遍**，只为了找 `target - nums[i]` 这一个值。「扫一遍找某个值」正是哈希表最擅长的事。这层循环被替换掉，`O(n²)` 就变成了 `O(n)`。

### key 和 value 分别存什么

- **key 存数值**，因为你查的是 `target - x` 这个数值。
- **value 存下标**，因为题目要返回的是下标。

如果只要判断「有没有」，value 就不要了，`set` 就够。**value 存什么，完全由题目要你返回什么决定** —— 这是哈希题里一个通用的小判断。

### 关键：边遍历边查

这是最容易写错的地方。直觉上会想先把整个数组塞进哈希表，再遍历一遍查互补值 —— 看起来只是「两次循环 vs 一次循环」，其实是**错的**：

```python
def two_sum_wrong(nums: list[int], target: int) -> list[int]:
    """反面写法：先把所有数存进表，再遍历查互补值。"""
    seen = {x: i for i, x in enumerate(nums)}
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:
            return [i, seen[need]]     # ← 会用到同一个元素
    return []
```

拿 `nums = [3, 2, 4], target = 6` 跑一遍：建表后 `seen = {3: 0, 2: 1, 4: 2}`；`i = 0` 时 `x = 3`、`need = 3`，命中且 `seen[3] = 0` —— 返回 `[0, 0]`。**它把自己用掉了两次**：因为表是「完整」的，`need` 可能正好就是 `x`，而这个元素从来没被排除过。

正确做法是让「建表」和「查询」在同一次遍历里交替发生：

```python
def two_sum(nums: list[int], target: int) -> list[int]:
    seen = {}                      # 值 -> 下标
    for i, x in enumerate(nums):
        need = target - x
        if need in seen:           # 先查：此时表里只有 x 之前出现过的数
            return [seen[need], i]
        seen[x] = i                # 后存：保证不会查到自己
    return []
```

顺序就是全部：**先查后存。** 查的时候表里只有「`x` 之前出现过的数」，所以 `need` 若命中，一定来自前面某个不同的下标 —— 「同一个元素不能用两次」这个约束被结构性地满足了，不需要额外写 `if seen[need] != i`。

心算 `nums = [2, 7, 11, 15], target = 9`：`i = 0, x = 2` 时 `need = 7`，表还空着，存 `seen[2] = 0`；`i = 1, x = 7` 时 `need = 2` 命中，返回 `[0, 1]`。

再看 `nums = [3, 3], target = 6`：`i = 0` 存 `seen[3] = 0`，`i = 1` 时 `need = 3` 命中，返回 `[0, 1]` —— 两个 3 是合法答案，它们是**两个不同的下标**。先建表的写法在这里也会返回 `[0, 1]`，看似对，但这只是巧合：它在 `[3, 2, 4]` 上就露馅了。**一个解法「在某个用例上碰巧对」，不等于它是对的。**

> **注意**
>
> 如果题目要返回**所有**满足条件的数对，就不能「查到即返回」：先查、把命中的都记下来，**再**存当前值 —— 顺序依然不能反。反过来写（先存后查）在遇到 `2 * x == target` 时会把同一个元素配给自己，凭空多出一对。

## 题二：字母异位词分组 {/* s4 */}

> 给定一个字符串数组，将其中的字母异位词组合在一起，返回分好组的结果。

题目在问「哪些字符串属于同一类」。哈希表的 key 天然就是「类」，value 就是「属于这一类的元素列表」，结构非常直接：
```python
groups = defaultdict(list)
for s in strs:
    groups[key(s)].append(s)
```

难点只有一个 —— **`key(s)` 写什么。** 你得把「互为异位词」这个模糊的关系，翻译成一个能直接比较的、规范化的值。异位词的定义是「字母组成完全相同」，有两条路。

### 方案一：排序后的字符串当 key

```python
def group_anagrams_sorted(strs: list[str]) -> list[list[str]]:
    from collections import defaultdict

    groups = defaultdict(list)
    for s in strs:
        groups["".join(sorted(s))].append(s)   # key 是排序后的字符串
    return list(groups.values())
```

异位词排序后必然得到同一个字符串，所以排序结果是一个**标准形（canonical form）**：同标准形 ⟺ 互为异位词。代价在 `sorted(s)` 上 —— 对每个长度为 `k` 的字符串排序是 `O(k log k)`，总复杂度 `O(n · k log k)`。

### 方案二：26 位计数元组当 key

```python
def group_anagrams_count(strs: list[str]) -> list[list[str]]:
    from collections import defaultdict

    groups = defaultdict(list)
    for s in strs:
        cnt = [0] * 26
        for ch in s:
            cnt[ord(ch) - ord("a")] += 1
        groups[tuple(cnt)].append(s)           # key 是 26 长度的计数元组
    return list(groups.values())
```

标准形换成「26 个字母各出现几次」。异位词的这个计数向量完全相同，同样构成合法 key。注意 `tuple(cnt)` 那一步：**`list` 不可哈希，不能当字典的 key，必须转成 `tuple`** —— 这是 Python 分组题最常见的报错来源，`TypeError: unhashable type: 'list'`。

### 两种 key 的对比

| | 排序字符串 | 26 位计数元组 |
| --- | --- | --- |
| 构造单个 key | `O(k log k)` | `O(k)` |
| key 的长度 | `k` | 恒定 26 |
| 总复杂度 | `O(n · k log k)` | `O(n · k)` |
| 适用前提 | 任意字符集 | 字符集小且固定 |

结论：**字符集是小而固定的字母表时，计数元组更快** —— `O(k)` 对 `O(k log k)`，key 长度还恒定，哈希和比较的代价都不随 `k` 增长。但它有硬前提：**你得知道字符集是什么、开得出定长数组。** 换成「可能包含任意 Unicode 字符」，26 这个数字就不成立了，得开个覆盖全字符集的数组，比排序还浪费 —— 这时候老实回排序法。

> **提示**
>
> 计数法的小坑：**字符范围不一定是 `a`-`z`。** 出现大写字母时 `ord(ch) - ord("a")` 会算出负数或越界，`cnt` 索引到错误位置，你会得到一个「看起来正常但分组错误」的答案 —— 不报错，更难查。更稳妥的变体是 `tuple(sorted(Counter(s).items()))` 当 key，慢一点但不怕字符集变化。
>
> 顺带一提，滑动窗口那篇里的「找到字符串中所有字母异位词」用的是同一个标准形思路，只是那里比较的是**两个定长数组**而不是哈希 key —— 因为窗口长度固定，不需要真的建表。

## 题三：最长连续序列 {/* s5 */}

> 给定一个未排序的整数数组 `nums`，找出数字连续的最长序列（不要求序列元素在原数组中连续）的长度。要求 `O(n)` 时间。

### 为什么暴力是 O(n²)

排序再扫一遍数连续段是 `O(n log n)`，题目不允许。不排序的话，暴力是对每个数 `x` 都去试着往上数 `x+1, x+2, ...`：

```python
def longest_consecutive_brute(nums: list[int]) -> int:
    """暴力：每个数都当一次起点往上数。O(n^2)。"""
    num_set = set(nums)
    best = 0
    for x in nums:
        cur, length = x, 1
        while cur + 1 in num_set:
            cur += 1
            length += 1
        best = max(best, length)
    return best
```

这里每个数都被当成「序列起点」试了一遍。`nums = [1, 2, 3, ..., n]` 时，从 `1` 数到 `n`、从 `2` 数到 `n`、从 `3` 数到 `n`…… 总共 `O(n²)` —— **每个连续段被从头数了很多遍。**

### 巧妙之处：只从「起点」开始扫

关键观察：**在一个连续段里，只有最小的那个数才是「起点」。** `[1, 2, 3, 4]` 里只有 `1` 是起点 —— 其它数的 `x - 1` 也在数组里，所以它们都不是。于是判据就是一句话：

```python
if x - 1 in num_set:
    continue      # x 不是起点，跳过
```

有了这个判据，**每个连续段只会被完整扫一次，而且是从起点出发的**。总扫描量回到 `O(n)`：每个元素要么作为起点被访问一次，要么作为非起点成员被跳过，都是常数次。

```python
def longest_consecutive(nums: list[int]) -> int:
    num_set = set(nums)          # 关键一：用 set 把「在不在」降到 O(1)
    best = 0

    for x in num_set:            # 关键二：遍历 set 而不是 list
        if x - 1 in num_set:
            continue             # x 不是起点，跳过 —— 避免重复扫描
        cur = x
        length = 1
        while cur + 1 in num_set:
            cur += 1
            length += 1
        best = max(best, length)

    return best
```

### 为什么不排序也能做

因为哈希表替排序干了活。排序的作用是「让相邻元素挨在一起，从而顺着找下一个」；但如果你只是判断「某个数在不在」，**排序提供的顺序信息是多余的** —— `x + 1 in num_set` 一次 O(1) 查找就把「下一个数在不在」问清楚了。

> **值得记牢**：题目要求「数值连续」时，直觉会去排序；但只要查询是「某个确定的值在不在」，哈希就够了。**排序只在需要「有序遍历」或「范围查询」时才不可替代。**

心算 `nums = [100, 4, 200, 1, 3, 2]`，`num_set = {1, 2, 3, 4, 100, 200}`：

| x | `x-1 in set` | 动作 | 本条长度 | best |
| --- | --- | --- | --- | --- |
| 1 | `0` 不在 | 从 1 往上数：2、3、4 在，5 不在 | 4 | 4 |
| 2 | `1` 在 | 跳过 | — | 4 |
| 3 | `2` 在 | 跳过 | — | 4 |
| 4 | `3` 在 | 跳过 | — | 4 |
| 100 | `99` 不在 | 从 100 数，101 不在 | 1 | 4 |
| 200 | `199` 不在 | 从 200 数，201 不在 | 1 | 4 |

返回 4（序列 `1, 2, 3, 4`），正确。中间那三行「跳过」就是 `continue` 存在的全部意义 —— 没有它，`2` 会从 2 数到 4、`3` 会从 3 数到 4，做的是完全重复的工作。

还有一点：循环写的是 `for x in num_set` 而**不是 `for x in nums`**。用 `nums` 遍历的话重复元素会被重复处理 —— `nums = [1, 1, ..., 1]` 时循环体执行 `n` 次，用 `set` 只执行一次。**去重之后遍历，是这个写法的一部分。**

## 哈希表的代价：什么时候不该用 {/* s6 */}

### 代价一：空间是 O(n)

**用空间换时间，空间不白给。** 上面三道题的空间都是 `O(n)`。多数时候这划算，但两个场景要留意：数据量极大、内存吃紧时，额外的 `O(n)` 可能直接 OOM，这时排序 `O(n log n)` 时间 + `O(1)` 空间反而合适；流式数据 / 无法全部载入内存时，哈希表根本建不起来。

### 代价二：最坏情况不是 O(1)

「哈希表查找是 O(1)」这句是**平均**复杂度。哈希函数把 `n` 个 key 映射到 `m` 个桶，理想情况每个桶一个元素；但哈希函数选得不好、或 key 集中在少数值上时，大量元素挤进同一个桶，查找退化成在链表（或红黑树）上扫描。**最坏情况所有 key 冲突，一次查找 O(n)**，整题退回 `O(n²)`。

实际影响没那么可怕 —— Python 的 `dict`/`set` 哈希函数是内建的，带随机化种子防碰撞攻击，桶密度超过 2/3 自动扩容。日常刷题不用为这个担心，但面试被问到时，标准答案是：**平均 O(1)，最坏 O(n)，取决于哈希函数质量和负载因子。** 别只答前半句。

### 代价三：不保序，不支持范围查询

哈希表能高效回答「**某个确定的值在不在**」，回答不了「**比 100 大的最小的数是多少**」。

| 需求 | 该用什么 | 单次代价 |
| --- | --- | --- |
| 某个值在不在 | 哈希表 | 平均 O(1) |
| 值 → 频次 / 下标 | 哈希表 | 平均 O(1) |
| 有序遍历所有元素 | 排序 + 数组，或平衡树 | O(n) / O(log n) |
| 「最大/最小」「前 K 个」 | 堆 | O(log n) |
| 「≥ x 的最小值」这类范围查询 | 排序 + 二分，或平衡树 | O(log n) |
| 「区间内有多少个元素」 | 前缀和 / 树状数组 | O(1) / O(log n) |

> **问「某个具体的值在不在」——用哈希；问「满足某种顺序关系的元素是谁」——哈希帮不上忙，得用排序或者树。**

拿最长连续序列举例：它的查询问的是「`x + 1` 这个具体的值在不在」，所以哈希完全够用，而且比排序快。但如果题目改成「找出最长的连续序列，且序列里每个数的出现次数都大于 k」，需要的就是「带着频次信息有序地扫」，纯哈希不够了。

## 一个易错点：Python 里那几种写法 {/* s7 */}

### `in` 判断：`dict` 判键，不是判值

```python
d = {"a": 1}
"a" in d          # True —— 判的是「键」
1 in d            # False —— 不是找值
```

**`x in some_dict` 检查的是键。** 想查值就得写 `x in d.values()`，那是个 O(n) 线性扫描 —— 一旦写了这句，哈希的意义就没了。发现自己写 `in d.values()`，通常说明 key 和 value 的角色反了。`set` 只有键没有值，`x in s` 没有歧义。

### `defaultdict` vs `setdefault`

两个都是「取一个可能不存在的键，不存在就给默认值」，写法差别很小，坑差得很大。

```python
from collections import defaultdict

groups = defaultdict(list)
groups[key].append(s)      # 推荐：键不存在时自动建空 list，直接 append
```

`setdefault` 也能用，但它返回的是值：

```python
groups = {}
groups.setdefault(key, []).append(s)    # 正确：拿到 list 往里面 append
```

经典错法是把它当 `defaultdict` 用：

```python
groups = {}
groups[key] = groups.setdefault(key, []).append(s)   # 错！
```

`list.append()` 返回 `None`，这一行执行完 `groups[key]` 就是 `None`，append 进去的东西全丢了 —— 而且不报错，你只会看到值莫名其妙都是 `None`。

> **注意**
>
> `defaultdict` 还有个更隐蔽的副作用：**它「读」也会建键。**
>
> ```python
> d = defaultdict(list)
> if d["missing"]:      # 只是想判空 —— 结果 d 里凭空多了一个键
>     ...
> print(dict(d))        # {'missing': []}
> ```
>
> 本身无伤大雅，但后面要遍历所有键时就会多出你没打算放的键。**只是要「查一下」，用 `d.get(k)`，不要用 `d[k]`。**

### 汇总

| 场景 | 推荐写法 | 避免 |
| --- | --- | --- |
| 判键存在 | `k in d` | `k in d.values()` |
| 计数累加 | `d[k] += 1`（`defaultdict(int)`） | 每轮 `if k not in d: d[k] = 0` |
| 分组 | `defaultdict(list)` + `d[k].append(v)` | `d[k] = d.setdefault(k, []).append(v)` |
| 只是查一下 | `d.get(k)` | `d[k]`（`defaultdict` 下会建键） |
| key 是数组 | `tuple(cnt)` | `cnt`（`list` 不可哈希） |

## 小结 {/* s8 */}

- **核心就一句话：用空间换时间，把查找从 O(n) 降到 O(1)。** 哈希题的代码是机械的，难度在识别。
- **四个识别信号：是否存在 / 有没有重复、配对 / 互补、计数、分组。** 分组题先想清楚 key 怎么设计。
- **配对题的关键是「边遍历边查」。** 先建全表再查会让同一个元素被用两次 —— `[3, 2, 4], target = 6` 上返回 `[0, 0]` 就是这个坑。
- **分组题的 key 是标准形。** 排序字符串 `O(k log k)`，26 位计数元组 `O(k)`，但后者要求字符集小而固定；`list` 当 key 要转 `tuple`。
- **连续序列题的关键是「只从起点扫」。** `x - 1` 在集合里就跳过；顺手用 `set` 遍历做去重。
- **哈希不是万能：空间 O(n)、最坏 O(n)、不保序、不支持范围查询。** 要顺序关系就换排序或树。
- **Python 细节：`in` 判键、`defaultdict` 优于 `setdefault`、`d.get(k)` 不产生副作用。**

拿到题先不看代码，用三秒过一遍那四个信号。命中任何一个，就先按哈希写一版，再想能不能改成更省空间的解法。**先有解，再好解。**
