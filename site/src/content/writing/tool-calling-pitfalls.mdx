## 一个不会报错的 bug {/* s1 */}

工具调用这个名字很容易让人以为难点在"让模型选对工具"。真做起来会发现，选错工具顶多答非所问，用户看得见；真正难缠的是那些**不报错、日志干净、测试全绿**的问题。

我自己的项目里出过一次这样的：

> 用户在聊天页说"这笔订单不要了，帮我退了"。
>
> 模型调用 `create_refund` 工具。工具执行引擎有统一的超时保护，30 秒没返回就判超时；
> 超时之后按配置重试一次。
>
> 结果：**这个订单被退了两笔钱。**

第一次调用其实**已经成功了** —— 它写进了数据库，只是在返回的路上超了时。执行引擎并不知道这件事，它只知道"我没等到结果"，于是又调了一次。两次都成功，数据库里两条退款单，日志里两条正常的 INFO 记录。

这件事让我意识到：给模型挂上工具，只是把"调一次函数"变成了"在一个会超时、会重试、会被模型重新决策的循环里调函数"。**可靠性问题不是从工具里冒出来的，是从这个循环的边界上冒出来的。**

下面三节分别讲这个循环里最容易出事的三处：超时怎么判、写操作怎么保证幂等、什么错误才值得重试。

## 超时：判失败之后，谁来收拾残局 {/* s2 */}

### 先看一个反直觉的实现

最直觉的超时实现大概是这样：

```python
import asyncio

async def call_tool_with_timeout(tool, args, timeout=30):
    """最朴素的超时：超了就抛，让上层决定怎么办。"""
    try:
        return await asyncio.wait_for(tool.ainvoke(args), timeout=timeout)
    except asyncio.TimeoutError:
        raise ToolTimeout(f"工具 {tool.name} 超过 {timeout}s 未返回")
```

看起来没问题。但如果这个工具**是同步的**，被包在 `run_in_executor` 或 `asyncio.to_thread` 里执行，`wait_for` 就治不住它了。

原因是 `asyncio.wait_for` 取消的是**协程**。它能中断 `await` 这个动作，但取消不了那个已经在线程池里跑起来的线程 —— 线程没有"被 await 取消"这个概念。`wait_for` 抛 `TimeoutError` 的时候，工作线程通常**还在跑**，并且很可能在几百毫秒后把活干完。

> **注意**
>
> 这一点是我实际踩出来的：`asyncio.wait_for` 只能取消协程，取消不了跑在线程里的同步工具。
> 所以"超时"这个词在这里是失真的 —— 准确的说法是"**我这边不等了**"，而不是"**那边停了**"。

这就引出了超时真正的难点：**超时不是"工具失败了"，而是"我不知道工具到底发生了什么"。**

### 三种状态，不是两种

把超时当成"失败"，是把三态问题压成了二态：

- **确认失败**：工具明确抛了错，什么都没做成。重试安全。
- **确认成功**：拿到返回值。什么都不用做。
- **未知**：超时了 / 连接断了 —— 工具很可能已经写入了，也可能没有。**这才是致命的那个。**

对第三种情况，正确的处理不是"重试"，也不是"报失败"，而是**先想办法确认状态**，或者干脆不重试。具体怎么做，取决于工具本身有没有提供查询能力。如果这个写操作之后可以查"这笔退款单存在吗"，那就先查；如果没有这个能力，那就把这次调用当成"已发生"，交给人处理。

### 判失败之后，模型会怎么走

这一层也容易被忽略。工具超时的异常不是抛给用户的，是**抛回给模型的** —— 模型拿到 `ToolTimeout` 后要自己决定下一步。它可能：

- **换个工具重试**（比如把 `create_refund` 换成 `query_order` 确认一下状态）—— 这是好事
- **原样重试同一个工具** —— 这就是上面那个退两笔钱的直接原因
- **向用户道歉并结束这一轮** —— 用户体验上的下策，但至少安全

所以超时异常的**文案本身就是提示词**。把错误信息写成 `工具超时，操作可能已经生效，请先查询状态再决定是否重试`，模型的行为会明显不一样。这一点我在项目里验证过：给工具错误补上"是否可能已生效"的说明后，模型自己先查订单的比例上升了很多。

## 幂等：重试两次会不会退两笔钱 {/* s3 */}

超时那节留了个尾巴：**未知状态**。幂等就是解决它的正解，而重试只是它的一个绕不开的副作用。

### 幂等键

工业界最通用的做法是**幂等键（idempotency key）**：客户端为"这一次业务意图"生成一个唯一标识，服务端看到相同键就返回第一次的结果，不再执行第二次。Stripe 的 API 就是这么做的。

放到 Agent 场景里，键应该绑在**业务意图**上，而不是绑在 HTTP 请求上：

```python
import hashlib
from uuid import uuid4

def build_idempotency_key(session_id: str, tool_name: str,
                          args: dict, turn_id: str) -> str:
    """把同一次业务意图映射到同一个键。

    注意 turn_id 的用法：同一轮对话里对同一个工具的重复调用，
    应当被视为"同一次意图"，键必须稳定不变 —— 否则重试会生成新键，
    幂等就白做了。
    """
    raw = f"{session_id}|{tool_name}|{turn_id}|{sorted(args.items())}"
    return hashlib.sha256(raw.encode()).hexdigest()
```

关键在 `turn_id`：**同一个用户意图在重试时必须拿到同一个键**。如果每次重试都新生成一个 `uuid4()`，服务端会认为是两次独立请求，幂等完全失效。这是一个看起来很小、但非常容易写错的细节。

服务端那侧的语义大致是：

| 键状态 | 服务端行为 | 返回给调用方 |
| --- | --- | --- |
| 不存在 | 正常执行，落库存键 | 首次执行的真实结果 |
| 已存在且已完成 | 不执行，直接返回缓存结果 | 与首次完全相同的响应 |
| 已存在但执行中 | 不重复执行 | 409 / 提示稍后再查 |

> **提示**
>
> 幂等键的存储必须和业务写入**在同一个事务里**。否则会出现"钱退了但键没存下"的窗口，
> 下一次重试照样会再退一笔 —— 你只是把窗口变小了，没有消灭它。

### 但不是所有工具都能幂等

现实里很多工具有副作用，业务上却不接受"补充一个幂等键"这种改造。比如发送短信通知、调用第三方物流接口下单。这时候能做的只有一件事：**承认它不幂等，然后别重试它。**

这就是我在项目里最终采用的方案：在工具构建期声明 `non_retryable`，把有副作用的工具从重试逻辑里排除出去。写操作绝不重试。幂等键是补充，不是替代。

## 重试边界：哪些错误值得再试一次 {/* s4 */}

前面两节回答的是"出事之后怎么办"，这一节回答的是**要不要让它出事**。

### 错误分类：先把错误分成三类

重试的前提是"这次失败是暂时的"。所以第一件事是给错误分类，而不是无差别重试：

- **可重试（transient）**：网络抖动、连接超时、上游 5xx、限流（429，带 `Retry-After` 时尤其要遵守）。这类错误的共同点是**过一会儿可能就好了**，而且**没有副作用**。
- **不可重试（permanent）**：参数校验失败、业务规则拒绝（余额不足、订单已关闭）、鉴权失败（401/403）。这类错误**重试一万次结果都一样**，只会放大延迟和成本。
- **未知**：超时、连接中断这类。前面说过了 —— 这类**不能因为"失败"就重试**，得先确认状态。

> **注意**
>
> 这里有个常被忽略的坑：**模型生成的参数错误，和业务返回的参数错误不是一回事。**
> 前者重试时应该把错误信息喂回模型让它改参数；后者重试没有意义。
> 如果不加区分，你会看到 Agent 拿着一个格式错的参数，对着同一个 API 硬打五次。

### 黑名单：不去猜，直接在构建期声明

错误分类解决了一半问题 —— 但还剩一个更根本的问题：**一个工具是否可重试，跟它这次报了什么错关系不大，跟它本身的副作用关系很大。**

所以我最后没有把判断放在运行时，而是放在**构建期**：

```python
from dataclasses import dataclass, field
from typing import Callable

@dataclass
class ToolSpec:
    name: str
    fn: Callable
    # 构建期声明：这个工具是否允许被重试
    retryable: bool = True
    # 允许的最大重试次数（不含首次调用）
    max_retries: int = 2
    timeout: float = 30.0

# 注册时明确标记，而不是运行时去猜
REGISTRY: dict[str, ToolSpec] = {}

def register(spec: ToolSpec) -> ToolSpec:
    REGISTRY[spec.name] = spec
    return spec

# 有副作用的工具：注册时就把重试关掉
register(ToolSpec(name="create_refund", fn=create_refund,
                  retryable=False))
register(ToolSpec(name="send_notification", fn=send_notification,
                  retryable=False))

# 只读工具：重试是安全的
register(ToolSpec(name="query_order", fn=query_order,
                  retryable=True, max_retries=3))
register(ToolSpec(name="search_faq", fn=search_faq,
                  retryable=True, max_retries=3))
```

「构建期」这三个字是关键。运行时判断意味着判断逻辑会分散到每个工具内部，而工具的作者会默认自己"应该被重试"—— 结果就是有副作用的工具悄悄混进了重试池。在注册那一刻显式声明 `retryable`，等于给每个工具打一个不可绕过的标签，后面所有执行路径都读这个标签。

### 退避怎么算

确定要重试之后，间隔不能是固定值：

```python
import asyncio
import random

def backoff_delay(attempt: int, base: float = 0.5,
                  cap: float = 8.0) -> float:
    """指数退避 + 抖动。attempt 从 0 开始计（首次重试 = 0）。

    抖动（jitter）不是可选项：同一次故障往往会让一批请求同时失败，
    没有抖动的话它们会在同一时刻一起回来，把小故障砸成大故障。
    """
    delay = min(cap, base * (2 ** attempt))
    return random.uniform(0, delay)   # full jitter

async def call_with_retry(spec: ToolSpec, args: dict):
    if not spec.retryable:
        # 写操作：一次性调用，超时不重试，交给上层确认状态
        return await call_tool_with_timeout(spec, args, spec.timeout)

    last_exc = None
    for attempt in range(spec.max_retries + 1):
        try:
            return await call_tool_with_timeout(spec, args, spec.timeout)
        except PermanentToolError:
            raise                      # 不值得重试，立刻上抛
        except RetryableToolError as exc:
            last_exc = exc
            if attempt == spec.max_retries:
                break
            await asyncio.sleep(backoff_delay(attempt))
    raise last_exc
```

这里用 **full jitter**（在 `[0, delay]` 均匀取值）而不是固定退避，是 AWS 那篇关于指数退避与抖动的经典建议的默认选择 —— 它也最容易实现、效果足够好。

### 什么时候必须停下交给人

有一类失败，重试和降级都救不了，只能停下来。我的判断线是三条：

1. **写操作状态未知，且无法查询确认**。别猜，直接把这轮挂起，让人看一眼。
2. **同一个工具在同一个会话里连续失败超过阈值**。这通常说明是系统性问题（服务挂了、凭据过期了），继续重试只会烧钱。
3. **错误涉及资金、法律或不可撤销的动作**。比如退款金额超过某个额度、删除数据。这类操作连"自动重试"都不该有，应该走人工确认。

停下来的方式也很重要：不要只是抛一个异常让模型继续瞎试，而应该**给用户一个明确的界面**。我在项目里用的是 LangGraph 的 `interrupt` 机制 —— 图在工具节点前中断，把当前状态和待确认的操作交给前端，用户点了"确认"之后用同一个 `thread_id` 恢复执行。这比让模型自己猜安全得多。

## 别把可靠性做成一道公式 {/* s5 */}

讲完这三节，我想泼一盆冷水：**上面这些做法不是配置项，是取舍。**

最大的那个取舍就在重试黑名单上。理论上"对所有工具都不重试"最安全 —— 绝对不会重复执行写操作。但我没有这么做，因为读操作超时重试是**安全且有效**的：工具超时里有相当一部分只是瞬时抖动，重试一次就回来了。一刀切地放弃重试，会明显降低整体成功率，用户看到的是"这个 Agent 老是答不上来"。

所以我的结论是一句判断，不是一组参数：

> **读操作重试，写操作绝不。**

这句话之所以能成立，前提是**你分得清读和写**。分不清的时候，就该回到构建期声明那里去 —— 别在运行时猜。

另外还有一处必须主动处理的失败，跟重试无关：**工具调用本身就没解析出来**。

模型返回的 tool call 参数是流式拼出来的 JSON。拼的过程中如果上游出错，或者模型自己生成了不合法的 JSON，LangChain 会把它们放进 `invalid_tool_calls`。这时候如果代码只读 `tool_calls`，就会拿到一个空列表 —— 于是这一轮既没有工具调用，也没有正常输出，**静默地什么都不返回**。用户看到的是一个空消息，日志里一切正常。

```python
calls   = getattr(acc, "tool_calls", None) or []
invalid = getattr(acc, "invalid_tool_calls", None) or []

# 工具调用 JSON 无法解析时，处理不当本轮会静默无输出
if not calls and invalid:
    raise ValueError(f"工具调用 JSON 无法解析：{invalid}")
```

主动抛错的代价是这一轮失败，比"静默无输出"好得多 —— 至少它在日志里留下了痕迹，也能被上层的重试或降级接住。

## 小结 {/* s6 */}

- **超时是三态问题**：确认成功、确认失败、状态未知。把未知当成失败，是最容易造成数据重复的错误假设。
- **`asyncio.wait_for` 取消不了线程里的同步工具** —— 超时只意味着"我不等了"，不意味着"那边停了"。
- **写操作的幂等键必须绑在业务意图上**，同一轮内的重试要复用同一个键；幂等键的落库要和业务写入同事务。
- **能不能重试应该在构建期声明**，而不是运行时猜。有副作用的工具注册时就关掉重试。
- **退避要带抖动**，否则故障恢复瞬间会被同时回来的请求二次击穿。
- **该停下的时候要停**：状态未知且无法确认、连续失败超阈值、涉及资金和不可撤销动作 —— 这三类交给人。
- 最后一条：工具调用 JSON 解析失败要**主动抛错**，不要让它变成静默的空输出。
