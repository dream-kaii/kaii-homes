## 一句只有四个字的话 {/* s1 */}

MewHelp 第六章上线之前，客服链路里跑着一段「意图分类」提示词，看着挺像回事：给定用户这一句话，从若干类里选一个，返回 JSON。它在我手写的测试句上基本都对，我就把它接进了主链路。

然后线上出现了这一句：

> 它能退吗

四个字，指代不明，没有主语也没有宾语 —— **但它不是一句坏话**，用户心里想得很清楚。真正的问题是：这五个字里没有足够的信息支撑任何路由决策。

我的判断按顺序错了两步：

1. **分类器先判了意图**。「退」这个字权重最高，于是拿到「退款类」的标签，一路走进**确定性的退款子流程**。
2. **子流程要订单号**。当前这句里当然没有，模型于是开始往回找 —— 它找到的那个订单号来自更早的上下文，属于另一笔交易。然后它按那个单号，走完了整个退款流程。

用户问的是「它」，系统退的是「它」之外的另一个单。整个链条上没有一个节点报错。

这件事让我把那一章的设计整个推翻了。原来我以为难点是「分类准不准」，实际上**分类器根本没在正确的时间点上被调用** —— 它拿到的是一个语义不完整的输入。这也是我把「指代消解和 Query 改写合一」放在意图识别之前的原因：不是流程好看，是顺序错了后面全错。

## 指代消解必须跑在意图识别前面 {/* s2 */}

### 为什么不能合成一步

最省事的想法是让模型「一边补全一边分类」，一个提示词解决两件事。我试过，它确实能跑，但出了问题你没法解释是哪一半坏的。

所以我拆成了两个节点，输入输出都很窄：

```python
async def resolve_coreference(query: str, history: list[dict],
                              summary: str | None = None) -> str:
    """把当前这句里的指代补成完整问句。

    输入只有：当前这句 + 最近几轮原文 + 更早历史的摘要。
    输出只有：一句改写过的话 —— 不产出任何路由决策。
    """
    rewritten = await llm.ainvoke(
        messages=build_coref_prompt(query, history, summary),
    )
    text = rewritten.strip()

    # 关键的安全阀：改写器允许「不改」，但不允许凭空造出实体。
    # 提示词里明确要求：找不到依据时原样返回，不要补任何东西。
    if not text:
        return query
    return text
```

拆开之后有三个具体好处，都是踩过坑才有的：

- **可以单独评估。** 我攒了一组「有指代」的样本，只测改写这一步对不对，不掺分类的噪声。混在一起评估时，你永远分不清是消解错了还是分类错了。
- **出问题能看见。** 改写结果要打进 trace。用户看到「它」被补成了什么，`Langfuse` 里一眼可见；只让模型内部「一边补一边分」，这一步就是黑盒。
- **摘要可以单独喂进来。** 注入顺序是固定的：人设、摘要、最近几轮原文、当前这句。

> **注意**
>
> 这里有个边界必须划清：**指代消解的目标不是「补全成一句好话」，是「补全成一句不含未知实体的完整问句」。**
> 我第一版的提示词写的是「补全用户想表达的意思」，模型就非常配合地开始猜 —— 缺订单号就顺着上下文挑一个最近的。
> 改法是把要求写死成一句：**找不到依据就原样返回**。宁可让后面那一步拿到一句不带指代的直白问句（「退货怎么操作」），也不要拿到一句看起来完整、实则带了个猜出来的订单号的问句。

### 一个具体的改写对照

| 当前这句 | 上下文里有什么 | 正确的改写 | 危险的改写 |
| --- | --- | --- | --- |
| 它能退吗 | 上一轮在聊订单 A，摘要里还有订单 B | 订单 A 能退吗（A 是上一轮明确讨论的那笔） | 订单 B 能退吗（挑了一个最近出现过的单号） |
| 这个多少钱 | 上一轮讨论的是某款商品 | 这款商品多少钱（保留指代对象，不展开） | 直接填一个型号进去 |
| 还是不行 | 没有任何明确对象 | 原样返回，交给下一步澄清 | 「订单 A 还是不能退款」 |

后一列不是假想的失败。**第一行和第三行我都真实遇到过** —— 第二行那种「善意补全」看起来最无害，其实同样是把「不确定」偷偷变成了「确定」。

## 八类意图：兜底比准确率重要 {/* s3 */}

### 类目要固定，但固定不等于够用

后端那套「流程有有限分支」的心智模型在这里还是好用的：类目是一个**固定的枚举**，主链路只认这个枚举里的东西。MewHelp 里它落在**八类**上，每一类带一个置信度。大概是这个样子：

```python
from enum import Enum

class Intent(str, Enum):
    LOGISTICS = "物流查询"
    REFUND    = "退款退货"
    ORDER     = "订单状态"
    PRODUCT   = "商品咨询"
    POLICY    = "规则政策"
    COMPLAINT = "投诉"
    CHITCHAT  = "闲聊"
    OTHER     = "其他"        # ← 最重要的一类

CONF_THRESHOLD = 0.6          # 低于这条线就不按分类结果走主链路

def route(intent: Intent, confidence: float) -> str:
    """把分类结果映射到流程分支。拿不准的一律走澄清，不硬猜。"""
    if intent is Intent.OTHER or confidence < CONF_THRESHOLD:
        return "clarify"      # 弹选择器，让用户点
    if intent is Intent.COMPLAINT:
        return "handoff"      # 固定兜底话术 + 转人工，不进 Agent
    if intent is Intent.REFUND:
        return "refund_flow"  # 确定性子流程，槽位缺失时挂起等用户补
    return "agent"            # 其余交给主力 Agent 节点自由决策
```

> **提示**
>
> `OTHER` 不是为了「把分不准的样本藏起来」，恰恰相反：**它是系统里唯一被允许承认「我不知道」的地方。**
> 没有这一类，模型必须在八选一里挑一个最像的 —— 所有拿不准的请求都会被塞进最热门的那一类，而最热门的那一类一般是退款。

### 降低准确率的做法，反而让系统更稳

这是我做这一章时最反直觉的决定：**我主动把「强行分类」砍掉了，分类准确率在评估集上是下降的。**

因为 `OTHER` 和低置信度分流不是「更聪明的分类」，是**更少的路由决策**。原来样本里大部分直接被分进某个业务分支，其中有些是猜的；现在剩下的走澄清。表面上「自动处理率」掉了，但**走错分支的代价比多问一句高得多** —— 走错退款流程会直接动数据，多问一句只花用户一次点击。

### 「多问一句」不能是再问一遍

第一版澄清的真实问题：用户说「它能退吗」，系统回「请问您想咨询哪类问题？」—— 用户的第一反应是「我刚才不是说了吗」。他要重新组织语言，要猜系统的分类体系。

所以澄清必须是**选择器**，不是开放式提问：

```text
用户：它能退吗

──────── lan 提示 ────────
你是想咨询下面哪一项？
[ 订单 A（2026-09-20 下单）怎么退 ]   ← 依据上一轮上下文生成的具体选项
[ 订单 B（2026-09-05 下单）怎么退 ]
[ 退款多久到账 ]
[ 都不是，我换个说法 ]
```

这里顺带说清楚两个别混淆的东西：

- **八类意图**是**会话维度**的分流，决定这一句话走哪条路 —— 它是那一章的主链路组件。
- **17 类主题分类**是第十章才出现的、**单句维度**的知识归类，用来回答「池子里的问题主要缺哪块知识，先补哪个类目」。它是一个批量旁路跑的微调小模型（RoBERTa 全参微调 + ONNX 推理），**不在实时链路里**。

这两个东西长得很像（都是「分类成 N 类」），回答的问题却完全不同：一个是「这句话该怎么处理」，一个是「这个问题属于哪个知识类目」。我把这两件事明确解耦了，因为它们连评估集都不该共用。

## 分错了怎么恢复 {/* s4 */}

兜底解决了「拿不准」，还剩「笃定地分错」。这一类只能靠恢复机制，不能靠提示词。

### 三个恢复点

我在这一章里留了三处可回退的位置，成本从低到高：

1. **子流程的槽位校验**。退款子流程第一步就检查「有没有合法的订单号」。这一步拦住的是刚才那类事故 —— 上一版的问题是子流程压根没做这一步，直接拿模型给的字符串去查。
2. **留痕 + 复用**。分类结果写进会话状态和 trace，带上置信度。用户下一句说「不是这个」，上一轮的分类就不会被当成既定事实重放。
3. **写操作前的确认**。这是最后一道，也是最硬的一道。第六章的退款子流程是确定性的，但**推进到真正动数据之前一定会挂起**，走 `interrupt` 把待确认的意图对象交给前端。这一段和第四篇里讲的重试边界是同一套思路：**语义问题可以交给概率模型，权限问题不行。**

> **注意**
>
> 判断分错的时候，**不要指望模型自己说「我可能分错了」**。它对错误分类的置信度通常和对正确分类一样高。
> 真正有效的信号来自**外部的确定性检查**：子流程要的槽位填不上、工具参数校验不过、用户下一句出现了否定表述。
> 这些都不是模型的一部分，是骨架的一部分。

### 分错了以后，别让「错」被复用

这一条和上下文那篇的教训同源。用户第一句被误判成退款，第二句说「我不是要退款，我问的是发票」。如果第二句的分类提示词里带着第一句的标签，模型很容易顺着往下走。我的做法是：**会话状态里只记录最近的分类结果 + 置信度，不把「历史意图链」拼进提示词** —— 让每一句的判定基于它自己和上下文事实，而不是基于自己的上一个结论。

## 有些请求根本不该进 Agent {/* s5 */}

这一节跟分类准不准无关，是我写这一章之前就吃过亏的地方。

### 三类请求应该被挡在入口

| 类型 | 特征 | 处理方式 | 为什么不能进 Agent |
| --- | --- | --- | --- |
| 情绪化表达 | 「你们这东西真垃圾」「我要投诉」 | 固定兜底话术 + 转人工 | 用户的诉求是「被回应」，不是「被解答」。Agent 越努力解释，越像在跟他抬杠 |
| 涉及金额 | 退款、赔付、优惠券补偿 | 确定性子流程 + 人工确认 | 金额动作是不可撤销的。类目固定、步骤固定，本来就不需要概率模型临场发挥 |
| 涉及权限 | 改地址、改账号信息、查别人的订单 | 确定性流程 + 鉴权 | 「能不能做」是权限问题，不该由模型判断 |

我在城觅做客服模块的时候见过第一种情况的后果：用户在抱怨「这单怎么这么慢」，Agent 特别积极地调了取消接口 —— 它把「抱怨」理解成了「诉求」。后来改成三段式（模型只提议、用户确认、系统执行），才把这条堵上。

### 为什么这个判断必须写在流程节点上

因为**提示词拦不住它**。这一点我在两张提示词上验证过：写「当用户表达不满时不要调用任何写操作」的时候，模型大部分时候听，偶尔不听；而「不听」的那一次，通常正是用户情绪最激动、语义最模糊的时候 —— 也就是代价最大的时候。

所以这条规则最后落在 LangGraph 的**条件边**上：意图是「投诉」或者检测到情绪化表达的，**图上根本没有通往 Agent 节点的那条边**。

```python
def after_intent(state: SessionState) -> str:
    """条件边：决定这个请求走哪条路。返回的是图上真实的边名。

    注意这里没有「万一模型想进 Agent 就让它试试」的分支 ——
    权限和金额相关的路径是排他的，写在边上而不是写在提示词里。
    """
    if state.intent is Intent.COMPLAINT:
        return "handoff"          # 图里 handoff 是终点，不存在后续节点
    if state.intent is Intent.REFUND:
        return "refund_flow"      # 确定性子流程，缺槽位则 interrupt
    if state.intent is Intent.OTHER or state.confidence < CONF_THRESHOLD:
        return "clarify"          # 弹选择器，等用户点
    return "agent"                # 只有这一类才进主力 Agent
```

这跟 Anthropic 那篇文章里反复讲的取舍是同一件事：能找到固定路径的，就别用动态决策。反过来，**动态决策的适用范围越窄，它出错的机会就越少** —— 这也是「让模型知道自己不该管什么」最实际的落脚点。

## 它不是一次分类，是一个契约 {/* s6 */}

回到最开始那句话：「它能退吗」。

现在它在这条链路上会走成这样 ——

1. 指代消解看到上一轮在聊订单 A，补成「订单 A 能退吗」；如果上下文里根本没有明确对象，原样返回。
2. 分类判成退款类，置信度 0.72，过线。
3. 子流程校验槽位，订单号 A 存在，合法，继续。
4. 推进到写操作前挂起，前端渲染确认卡，用户点了「确认」才恢复执行。

而如果第 1 步拿不准、第 2 步置信度只有 0.45，它会变成一个**选项列表**，而不是一个猜出来的答案。

回头看，这一章真正的产出不是那个分类提示词，是**三处「允许系统说不知道」的地方**：指代找不到依据时原样返回、意图拿不准时归入「其他」、槽位缺失时弹选择器。这三处加上「投诉根本不进 Agent」的那条边，构成了一个契约：**系统知道自己负责哪一段，也知道哪一段该交出去。**

还有一处跟它是同一类失败：工具调用的 JSON 解析不了的时候，如果只是忽略，本轮**静默无输出** —— 用户看到一个空消息，日志一片干净。这和「指代消解猜了个订单号」是同一个病：**系统在不确定的时候，选择了沉默地继续。**

```python
calls   = getattr(acc, "tool_calls", None) or []
invalid = getattr(acc, "invalid_tool_calls", None) or []

# 解析不了就主动失败，不要让它变成一轮空回答
if not calls and invalid:
    raise ValueError(f"工具调用 JSON 无法解析：{invalid}")
```

## 小结 {/* s7 */}

- **指代消解必须跑在意图识别前面。** 顺序错了，后面每一步都在一个语义不完整的输入上做决策 —— 而且它不报错。
- **改写器的安全阀是「找不到依据就原样返回」**，不是「尽量补全成一句好话」。前者把「不知道」传下去，后者把「不知道」伪装成「确定」。
- **八类意图里，「其他」类是核心不是补丁。** 没有它，所有拿不准的请求都会被塞进最热门的那一类。
- **主动降低自动处理率是可以接受的取舍**：多问一句的成本，远低于走错一条会动数据的分支。
- **澄清必须是选择器，不是开放式提问。** 让用户点，不要让用户重新组织语言。
- **分错了靠恢复机制而不是提示词**：子流程槽位校验、分类留痕不复用、写操作前确认。
- **投诉、情绪化表达、涉及金额和权限的请求不该进 Agent。** 这条要写在图的边上，不要写在提示词里。
- 别混淆两个分类器：**八类意图**是会话维度的实时路由，**17 类主题**是单句维度的离线知识归类。
