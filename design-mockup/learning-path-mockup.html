学习路线

这里记录我自己走过的三条线，以及踩过的弯路。每条路线按「先做什么、再做什么」的顺序排开， 每一步都能点进我写的对应文章 —— 官方文档放在文末作为补充，不单独占一步。

标注「待写」的是已规划、还没动笔的

先想清楚一件事：你要建的是 Workflow 还是 Agent

很多人一上来就问「用哪个框架」，这是错的问题。Anthropic 在他们的工程博客里给过一个很清楚的区分 —— 大多数场景用固定的 workflow 就够了，硬上 Agent 只会换来更慢、更贵、更难调。 建议先花十分钟把概念理清，再决定要不要上「Agent」这个词。

STEP 01
能对话
模型调用、流式输出、多轮上下文
STEP 02
能动手
Function Calling，模型自己选工具
STEP 03
有知识
RAG：切块、嵌入、检索、重排
STEP 04
有骨架
图编排、上下文、人工确认
STEP 05
能上线
工具系统、观测、评估、飞轮
01

先读概念，别急着写代码 半天

动手前先把「Workflow 和 Agent 到底差在哪」搞清楚。这不是学术问题 —— 它直接决定你的架构选型。 Anthropic 那篇是业内被引用最多的入门材料，讲清了五种 workflow 模式，也明确说了什么时候不该用 Agent。

重点看这两句：「Workflows 是预定义代码路径编排 LLM 和工具」「Agents 是 LLM 动态决定自己的流程」。想清楚你的场景属于哪一种。
待写 我用一个客服场景讲清 Workflow 和 Agent 的分界

02

把一次对话调通 1-2 天

不要用框架起步。建议先直接用模型 API，很多模式几行代码就能实现。 你需要亲手写一遍 HTTP 调用、处理流式返回、拼装多轮消息，才能理解框架在替你做什么。

目标很朴素：能用 curl 或十几行 Python 拿到一次流式回复，并让第二句话接得住第一句的上下文。 

# 用原生 HTTP 理解本质，再上框架
curl https://api.deepseek.com/v1/chat/completions \
  -H "Content-Type: application/json" \
  -H "Authorization: Bearer $API_KEY" \
  -d '{"model":"deepseek-chat",
       "messages":[{"role":"user","content":"你好"}],
       "stream": true}'
各家上游现在基本都兼容 OpenAI 协议。把 base_url、model、api_key 全放进环境变量，之后换供应商就不用改代码。
待写 从零跑通一次流式对话：那些框架替你做的事
03

让模型会调工具 3-5 天

Function Calling 是 Agent 的分水岭。核心只有一件事：你把可用的函数描述给模型，它自己决定什么时候调、传什么参数。 框架会帮你把「模型要调工具 → 执行 → 结果回灌 → 生成回答」这个循环封起来。

Anthropic 有个反直觉的观察：他们做 SWE-bench 的 Agent 时，花在优化工具定义上的时间比优化提示词还多。 工具的命名、参数、描述，就是模型的世界观。

已有 工具调用的三个工程问题：超时、幂等与重试边界
文档 LangChain · Tools ↗ Agents ↗
04

给模型接上自己的知识 1-2 周

RAG 是这条路上坑最多的一站。顺序别乱：先切块 → 再嵌入 → 存向量库 → 检索 → 加引用。 很多人一上来就纠结用哪个向量库，其实切块策略对效果的影响远大于换个数据库。

已有 从关键词到语义：为什么 RAG 一定要做混合检索
05

用图编排把稳定部分焊死 1 周

到这一步你会发现：光靠提示词约束不住模型。像「知识类问题必须先检索」「投诉不要进 Agent」这种规则， 写在提示词里模型随时可以不听 —— 要用确定性的流程节点把它固定下来。

06

接外部工具生态 3-5 天

MCP 是这两年被推得最广的一套协议，本质是「让 Agent 统一地接上外部工具和数据源」。 官方文档把它类比成 USB-C：一份实现，到处能插。自己写一个 MCP Server 是最快的理解方式。

07

让它能被运维 持续

这一步最容易被跳过，但它是「玩具」和「系统」的分界线：可观测（每次调用的完整链路）、 评估（检索和回答质量怎么量化）、成本（钱花在哪类问题上）、数据飞轮（答不上来的问题怎么变知识）。

Anthropic 的三条原则里有一条就是：优先透明，显式展示 Agent 的规划步骤。可观测不只是排障手段，也是设计要求。
待写 从玩具到系统：Agent 上生产前必须补的四件事

刷题不是刷数量，是按题型建立反射

建议先把题型分类过一遍，再按分类集中攻克，而不是从第 1 题顺着做到第 100 题。 同一类题连做 5-8 道，才能形成「看到这类问题就知道用什么套路」的反射。

DP · 贪心

01

先建地图，再开始走 1 天

开始刷之前先看一眼按题型组织的路线图，知道整个版图有多大、哪些是主干。 这样你每做一道题都知道它属于哪一类，而不是零散地记题。

不要一开始就按题库编号刷。按题型集中攻克的效率，比顺序刷高得多。

02

Hash 表：从「我会写」到「我秒懂」 3 天

这是性价比最高的一类。核心只有一句话：用空间换时间，把查找从 O(n) 降到 O(1)。 掌握之后，两数之和、字母异位词、最长连续序列这些都变成同一个套路。

判断标准：看到「是否存在」「有没有重复」「配对」这类字眼，你应该下意识想到 Hash。

待写 Hot 100 哈希专题：识别信号再用套路
03

双指针与滑动窗口 1 周

面试出现频率最高的一类。两种形态要分清：双指针解决「有序数组里找配对」， 滑动窗口解决「连续子串/子数组满足某条件」。

待写 滑动窗口题型的统一思路
04

链表：考的是指针操作 3 天

套路非常固定：哑结点（dummy）简化边界、快慢指针找中点/判环、反转用三指针。 把这几招练熟，链表题基本不会挂。

做链表题一定要画图。在纸上画出指针的移动过程，比在脑子里想快十倍，而且不容易错。
待写 链表题的指针套路整理
05

树与图：递归思维的分水岭 1-2 周

树题看起来多，其实都是同一个模板：「这个问题，我的左右子树分别是什么答案？」 把递归的「定义」想清楚，代码自然就出来了。

BFS 用队列、DFS 用递归或栈 —— 这两句话能覆盖绝大多数图的遍历题。

待写 二叉树遍历：把递归的「定义」想清楚
06

动态规划：最后再碰 2-3 周

DP 是最容易劝退的一类，建议放到最后。前面的基础没打牢时硬啃 DP，只会打击信心。

入门后有固定思考顺序：① 定义状态 ② 找转移方程 ③ 确定初始条件 ④ 考虑空间优化。 关键是第 ① 步 —— 把状态定义说清楚，题就解了一半。

如果一道题卡了 30 分钟还没思路，直接看题解。刷题的目的是学会套路，不是证明自己聪明。
待写 动态规划入门：先学会定义状态

先把会用变成懂原理，再谈分布式

后端的路线我建议这样走：语言基础 → MySQL → 框架 → Redis → 分布式与中间件 → 最后回到 JVM 底层。 把 JVM 放最后不是因为不重要，而是因为它解释的是「前面这些为什么会有性能问题」—— 没有前面的实践，硬啃内存模型和 GC 只会变成背结论。

01

语言基础：从「会用」到「知道它怎么实现」 1-2 周

先打牢 Java 语法、面向对象、异常处理这些基本功，然后重点啃 集合框架。 面试最爱问的也是这里 —— 但别背「HashMap 默认容量是 16」这种结论，要能讲清为什么。

为什么用数组 + 链表 + 红黑树？为什么扩容是 2 倍？为什么负载因子是 0.75？ 这几个问题背后是同一件事：在时间、空间和哈希冲突之间找平衡。

待写 HashMap 的每个设计决策，背后的权衡是什么
02

MySQL：先会写，再懂它为什么慢 1-2 周

从能写 SQL、能设计表开始，然后吃透索引。核心是两个问题： B+ 树为什么适合做索引（矮胖、范围查询友好、磁盘 IO 次数少），以及什么情况下索引会失效。

事务部分要能讲清四种隔离级别分别解决了什么问题，以及 MVCC 是怎么让「读不加锁」成为可能的。

检验标准：给你一条慢 SQL，你能用 EXPLAIN 看出它为什么没走索引。
待写 从一条慢 SQL 说起：索引为什么失效
03

框架：先会用，再理解它替你做了什么 1-2 周

从 SpringBoot 起步最容易上手 —— 但不要停在「能跑起来」。 依赖注入、AOP、自动配置这三块是 Spring 的骨架，理解了它们，你才知道为什么加个注解就能生效。

建议顺序：先能写出一个完整的分层 CRUD，再回头读 SpringBoot 的自动配置原理。 有了实践再看原理，理解会快很多。

待写 Spring 的依赖注入到底解决了什么问题
04

Redis：重点不在会用，在知道会怎么坏 1 周

先学会五种基础数据结构各自的适用场景，然后重点理解缓存会怎么出问题： 穿透、击穿、雪崩分别是什么、怎么防，以及缓存和数据库的一致性该怎么做。

这几个问题最好的练法，是自己写一个秒杀功能 —— 库存扣减、一人一单、防超卖， 这些需求会逼着你把 Redis 的原子操作真正搞明白。

待写 缓存穿透、击穿、雪崩：三种病，三种药
实践 可对照「城觅」项目的秒杀链路
05

分布式与中间件：多个进程怎么协作 2-3 周

到这里要处理的问题变成「多个进程之间怎么协作」： 消息队列解决削峰和异步解耦，分布式锁解决跨进程的互斥， 再往上就是微服务的拆分、网关与链路追踪。

这一层最关键的概念是幂等：消息可能重复投递，所以你的消费逻辑必须能被执行多次而不出错。 这是从「会用」到「能上生产」的分界线。

最忌讳只背概念。建议找一条真实链路（下单 → 扣库存 → 发消息 → 通知）完整走通一遍，比看十篇文章都管用。
待写 为什么消息队列一定要考虑幂等
06

JVM 与深度原理：回头解释前面的一切 2-3 周

放到最后不是因为它不重要，而是因为它是对前面所有内容的统一解释。 有了秒杀、缓存、微服务的实践之后再来学 JVM，你会不断产生「原来当初那个问题是这个原因」的感觉。

重点不是记住分代的名字，而是理解「为什么这样分」：大多数对象朝生夕死，所以新生代用复制算法； 老年代存活率高，所以用标记整理。

能讲清「一次 Young GC 的完整过程」和「什么情况下对象会晋升到老年代」，这一块就算过关。
