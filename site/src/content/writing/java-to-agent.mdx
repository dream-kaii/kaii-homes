## 一个真实的起点 {/* s1 */}

在城觅的秒杀链路里我接过一个客服需求：用户下单后想取消，问一句「帮我退了吧」，系统得能查订单、判断状态、发起退款。

我的第一反应是写状态机。订单有 `待支付 / 已支付 / 已发货 / 已取消`，取消动作有几个前置校验，画一张状态转移图，每条边写一个 Service 方法，三天能做完。

后来我把它改成了 Agent 版本。模型接到这句话，自己决定先调 `query_order` 拿订单号，再调 `check_refundable` 看能不能退，最后调 `cancel_order` 落库。我没写状态转移图，只提供了一个工具清单。

跑起来的那一刻是有点震动的。但接下来一周，我遇到的问题一个都不是「模型聪不聪明」：

- 模型在用户只是抱怨「这单怎么这么慢」的时候，也顺手发起了取消
- `query_order` 超时被重试，取消动作跟着执行了两遍
- 对话讲到第八轮，历史被裁剪，工具调用链从中间断掉，之后每一轮都失败

修完这三个问题我意识到，**这些坑我都见过**。超时重试、幂等、上下文裁剪的边界 —— 城觅的秒杀链路里，这些问题以另一个名字出现过。

所以这篇文章想讲的不是「Java 人怎么速成 AI」，而是**你已经有的东西里，哪几块能直接搬过去，哪几块必须换掉**。

## 可以直接平移的部分 {/* s2 */}

先说结论：后端那套工程素养在 Agent 领域不是「能凑合用」，是**真的稀缺**。我见过不少能调通 LangChain 的人，写出来的东西在生产上撑不过一天。

### 异常处理：从「抛出去」到「说不清」 {/* s2a */}

Java 里异常是个明确的对象：`catch (Exception e)` 之后你有 message、有 stack trace、有类型。Agent 里最大的问题是**失败经常不带异常** —— 模型答非所问不报错，工具返回一个语义错误的 JSON 不报错，上下文超限被上游拒绝时报的只是 `400 Bad Request`，你得自己认出是 token 超了。

所以 Agent 里更常见的做法是**主动失败**：与其让一个空回答流到用户面前，不如显式抛出去。MewHelp 的工具执行链里我加了一段：
```python
# 工具调用 JSON 无法解析时，如果只是忽略，本轮会静默无输出
calls   = getattr(acc, "tool_calls", None) or []
invalid = getattr(acc, "invalid_tool_calls", None) or []

if not calls and invalid:
    raise ValueError(f"工具调用 JSON 无法解析：{invalid}")
```

> **提示**
>
> 这个 `raise` 不是「防止错误」——错误已经发生了，它的作用是**让错误可见**。后端人对这个词应该非常熟：fail fast。

### 幂等：Agent 领域比后端更需要 {/* s2b */}

后端做幂等是为了应对「用户重复点击」和「消息重投」。Agent 领域多出来一个来源：**重试**。

我在 MewHelp 里踩过这个坑。工具执行引擎统一做了超时加重试，但 `asyncio.wait_for` 只能取消协程，**取消不了跑在线程里的同步工具**。超时触发重试后，一个执行过的写操作会被再执行一遍 —— 日志里一点异常都没有。修法是引入构建期的 `non_retryable` 黑名单：读操作照旧重试，有副作用的写操作绝不重试。

这个概念你在城觅里见过。秒杀链路的 Kafka 消费端异常会重试，但下单消息的重试不是「重放」，是**再执行一遍业务** —— 用户看到一次下单，库存掉了 2。当时的修法是按业务幂等键查重。

> **注意**
>
> 两边道理相同，但落点不同：后端的幂等键是**数据维度**的（用户 + 优惠券 + 时间片），Agent 的更像**操作维度**的（这个工具能不能被安全地调第二次）。
> 前者靠数据库唯一约束兜底，后者只能在调用前决定。

### 可观测性 {/* s2c */}

这块最能直接复用。智学云课堂那套体系里，一个请求穿过网关、鉴权、交易、促销，出问题要能定位到模块。Agent 里一条对话穿过意图识别、工具调用、检索、生成，同样是逐段定位 —— 区别只是后端接 SkyWalking，Agent 接 Langfuse，看的指标从 QPS 变成 token 数。

### 分层边界 {/* s2d */}

这条**最容易被忽略、价值最高**。Controller 不写业务逻辑，Service 不碰 HTTP，DAO 只管数据 —— 这些规则在 Agent 里同样成立，而且更要紧，因为模型的输出天然是「无边界」的。

我给自己定的一条：**工具层对外只暴露明确的输入输出契约，模型看不到数据库表结构**。检索从关键词换成向量后，工具对外的契约一行没改。

> **提示**
>
> 判断一个 Agent 项目结构好不好，有个很朴素的测试：
> **换掉模型厂商，需要改几个文件？** 如果答案是「到处都是」，说明边界没划好。

## 需要换掉的心智模型 {/* s3 */}

前面说的都是「能搬的」。但有一件事必须重新学，而且**根本性**：**确定性流程和概率流程的区别**。

### 从「分支覆盖」到「分布」 {/* s3a */}

后端写一个方法，你清楚它有几条路径。`if (stock > 0)` 要么进要么不进，测试覆盖两条分支就够了。
模型没有分支，只有分布。同一句「帮我退了吧」：今天调 `cancel_order`，明天先调 `query_order`，后天可能先安慰用户两句 —— 路径不是有限的，覆盖不全。

第一个后果是**测试的写法完全不同**：后端测试是「给定输入，断言输出」，Agent 这么写会极其脆弱 —— 模型换一句话你就红一片。我现在的做法是把断言从「输出是什么」改成「输出了什么性质」：

```python
def test_cancel_requires_confirmation():
    """写操作必须先出确认意图，不能直接执行。"""
    result = agent.run("帮我把这个单退了吧", session=SESSION_WITH_ORDER)
    assert result.pending_intent is not None
    assert result.pending_intent.tool == "cancel_order"
    assert not orders_repo.was_modified()   # 关键：数据没被改
```

注意最后那行。它检查的不是「模型说了什么」，是「**系统状态有没有被意外改掉**」—— 模型的输出不可控，但副作用必须可控。

### 确定性骨架 + 概率节点 {/* s3b */}

接受「模型会跑偏」之后，架构思路就变了：不设法让它不跑偏（做不到），而是**把跑偏的影响限制在一个格子里**。

MewHelp 第五章之前我用的是单轮工具调用：模型自己决定调哪个工具、调几次。简单场景够用，但接不住「先查订单拿单号、再查物流」这类多步任务 —— 中间步骤的失败没有被善后。

改成 LangGraph 图编排之后，结构变成：**流程骨架是确定性的，只有需要理解语义的那一步交给模型**。

```
[入口] → [意图分流（确定性规则）] → [主力 Agent 节点（模型）] → [工具执行（确定性）] → [出口]
                 ↑                                                    ↓
                 └──────────── 失败重试 / 降级（确定性）──────────────┘
```

这其实就是后端的责任链和状态机。**你在智学云课堂里写的编排逻辑，搬到 Agent 里几乎原样可用** —— 前提是你接受「有一个节点不可靠」，并围绕它设计重试和降级。

### 不让模型做权限判断 {/* s3c */}

城觅的客服模块里，我做过一个反直觉的决定：**AI 只负责提议，用户确认，系统执行**。

原因是踩过坑。最初让模型直接调写操作，它会做两件危险的事：一是在用户只是抱怨时提前发起写操作；二是在参数缺失时**编一个订单号**。对话里说「已为你取消」，数据库里订单还在。后来定了三段式：模型只生成一个待确认的意图对象，前端渲染成确认卡，用户点了才走既有的服务方法。

> **注意**
>
> 为什么不让模型自己判断「该不该确认」？因为「该不该动数据」是**权限问题，不是语义问题**，权限不该交给一个概率模型去决定。
> 这条在后端是常识，在 Agent 领域经常被忘掉 —— 因为模型说话太像人了。

## 缺口最大的：评估 {/* s4 */}

这一节是我认为**真正的门槛**，也是绝大多数 Agent 项目最弱的一环。问题很具体：**你改了一句 prompt，怎么知道变好了还是变坏了？**

后端不会有这个问题。改一段业务逻辑，跑测试，红了就是坏了。Agent 里你改一句话，昨天答对的问题今天答错了，而五十个昨天答对的还是答对 —— 你到底改好了没有？

### 唯一的解法是评估集 {/* s4a */}

我的做法很笨，但有效：

1. **攒样本**。不是凭空造，是从真实问题里收；MewHelp 答不上来的问题会进池子，人工审过之后挑典型的留下。
2. **每条样本标出「正确答案该来自哪一段 / 该调哪个工具」**。这比标「标准答案」容易也稳定 —— 模型的措辞会变，来源不会变。
3. **跑一套固定的检查**，记录通过率；改 prompt 前后各跑一遍，看数字。
关键是第 3 步要**自动跑**。评估集不能一条命令跑完，就没人跑，最后它就烂在那里。

### 评估的三个层次 {/* s4b */}

我现在会分三层看，成本从低到高：

| 层次 | 检查什么 | 成本 | 什么时候用 |
| --- | --- | --- | --- |
| 检索层 | 正确答案是否进入 Top-K | 低（不需要模型） | 每次改切块或检索策略 |
| 工具层 | 是否调了正确的工具、参数对不对 | 中 | 每次改工具描述或注册方式 |
| 生成层 | 答案是否正确、是否引用了来源 | 高（要调模型或人工审） | 里程碑节点，不是每次 |

这张表的作用是**省时间**。大部分改动只影响前两层，跑一次检索评估几秒钟出结果，不必动用贵的生成层。

> **提示**
>
> 检索层评估最划算：不调用生成模型，跑得快、几乎不花钱，还能定位到具体哪条样本、哪一段没被召回。
> 如果只能做一层，做这一层。

### 一个反直觉的观察 {/* s4c */}

评估集跑多了会发现：**改动的收益经常小于你花在评估上的时间**。

我在 MewHelp 里给检索加过一版混合检索（BM25 + 向量 + RRF + 重排）。加之前跑了一遍评估，发现纯向量在同义问题上已经够了，只在**型号类问题的精确度**上不够 —— 重排那一层起初并没有被数据支持。后来是数字告诉我：双路召回收益明显，重排的边际收益小得多。

> **注意**
>
> Anthropic 在他们的工程博客里反复强调同一件事：
> *find the simplest solution possible, and only increasing complexity when needed.*
> 没有评估集，你判断不了「需要」的边界在哪 —— 只会凭感觉越堆越复杂。

## 顺序：先手动跑通一次工具调用 {/* s5 */}

最后说路线。网上的路线图通常是「学 LangChain → 学 LangGraph → 学 RAG → 学微调」，一步步往上爬。我的建议不同：

> **先不碰框架，用 HTTP 请求手动跑通一次工具调用。**

这不是为了炫技，是为了**知道框架替你做了什么**。不用框架时，你会亲手处理这几件事：

1. 把工具定义转成模型能读懂的 JSON Schema
2. 拿到模型返回的 `tool_calls`，手动解析出函数名和参数
3. 执行函数，把结果按规定的格式塞回消息列表
4. 再次请求，看模型怎么用这个结果

```java
// 用 Spring 的 RestClient 手搓一次工具调用（伪代码，去掉样板）
// 目的：看清 OpenAI 兼容接口到底在传什么
var tools = List.of(Map.of(
    "type", "function",
    "function", Map.of(
        "name", "query_order",
        "description", "按订单号查询订单状态",
        "parameters", Map.of(
            "type", "object",
            "properties", Map.of("orderNo", Map.of("type", "string")),
            "required", List.of("orderNo")
        )
    )
));

var messages = new ArrayList<Map<String, Object>>();
messages.add(Map.of("role", "user", "content", "帮我查一下 ORD20260901001 到哪了"));

var resp = restClient.post()
    .uri("/chat/completions")
    .body(Map.of("model", MODEL, "messages", messages, "tools", tools))
    .retrieve()
    .body(Map.class);

// 关键一步：这里调出来的不是文本
var choice  = (Map<?, ?>) ((List<?>) resp.get("choices")).get(0);
var message = (Map<?, ?>) choice.get("message");
var calls   = (List<?>) message.get("tool_calls");
```

跑到这一步你会看到：`message.get("content")` 是 `null`，真正的动作在 `tool_calls` 里。这个细节在框架里被藏起来了，而它恰好是后面所有坑的源头 —— 上下文裁剪会拆散 `tool_calls` 和它的结果，重试会让写操作跑两遍。

之后的上手顺序：

1. **手搓一次工具调用**（不碰框架）—— 上面那一段
2. **用最小框架把多轮对话 + 工具跑通** —— 框架的价值从这一步才出现
3. **接检索，并且**做检索层评估 —— 评估和检索一起上，别等
4. **上编排** —— 当单轮调用接不住多步任务时再上，不是为了架构好看
5. **最后才是可观测、降级、微调** —— 这些是运营阶段的活

> **注意**
>
> 第 3 步到第 4 步之间，最容易被跳过的是评估。**评估集不是项目做完补的作业，是中途唯一的导航仪** —— 没有它，你判断不了「是因为编排才变好，还是因为别的原因」。

## 小结 {/* s6 */}

- **能平移的**：异常处理（fail fast）、幂等（尤其是重试带来的副作用）、可观测性、分层边界。这些不是「能用」，是 Agent 领域真的缺
- **要换掉的**：从「流程有有限分支」换成「模型每步都是分布」。测试断言从「输出是什么」改成「系统状态有没有被改坏」
- **缺口最大的**：评估。评估集不是作业，是导航仪；检索层的评估最划算，先做这一层
- **顺序上**：先手动跑通一次工具调用，再上框架和编排。知道框架替你挡了什么，才知道出问题时该往哪看

在城觅写秒杀链路时，我学会了「这条链路在生产上会不会断」这个问法。现在做 Agent，我还是先问这个，再问「效果好不好」。
