## 一个真实失败案例 {/* s1 */}

先看一个我自己撞上去的场景。客服 Agent 刚上线时，上下文处理写得很朴素：把整个会话历史
拼起来递给模型。前几轮没问题，聊到后面请求体越来越大，最后直接撞上上下文上限。

于是按 token 预算裁剪，思路也很朴素：**一问一答是一对，从最老的一对开始删。**
这个假设在纯聊天里完全成立。但客服会话里有工具调用 —— 用户问「我的订单到哪了」，实际发生的是：

```text
user: 我的订单到哪了
assistant(tool_calls): query_order(order_id="20260901001")
tool: {"status": "已发货", ...}
assistant: 您的订单昨天已经发出，预计明天到。
```

一条**对话轮**在这里其实是四条消息，最前面的 `user` 和最后面的 `assistant` 之间隔着一次工具调用。
成对裁剪只看「第几条是 user、第几条是 assistant」，压根不知道中间夹了东西。裁完之后变成这样 ——

```text
tool: {"status": "已发货", ...}     ← 窗口的第一条
assistant: 您的订单昨天已经发出……
user: 我还能改地址吗
```

窗口以 `tool` 开头，而 `tool` 消息在协议上必须紧跟在带 `tool_calls` 的 `assistant` 消息后面。
于是上游直接拒收。

> **注意**
>
> 这类失败最危险的地方在于：**它不报错在裁剪那一层**。裁剪函数正常返回、日志里没有任何异常，
> 只有上游 API 返回 400。更糟的是 —— 被裁掉的历史不会自己长回来，
> **从那之后的每一轮请求都会带着同一个坏窗口**，会话彻底卡死。
>
> 用户看到的是「客服忽然不会说话了」，你从监控上看到的就是一串看起来无关的 400。

修法在第五节展开。这里先记住一句话：**上下文裁剪不是数组切片，是在维护一个结构。**

## 滑窗：窗口开多大是算出来的 {/* s2 */}

滑窗解决的是「最近几轮保真」：越近的对话越重要，原文不能改。问题只剩一个：**开多大？**

绝大多数实现是拍一个数字，比如「保留最近 10 轮」，然后上线。这个数字在某种对话风格下刚好，
换个用户就爆或者就浪费。既然裁剪本来就是按 token 预算做的，窗口大小应该由预算**反推**出来：

```python
def window_params(ctx_limit: int, system_tokens: int, reserve_output: int,
                  reserve_retrieval: int) -> dict:
    """由模型上下文上限反推滑窗预算。

    ctx_limit        模型上下文上限
    system_tokens    system prompt + 工具 schema 的固定开销（每轮都要占）
    reserve_output   给模型回复留的空间，必须留，否则答案会被截断
    reserve_retrieval 给「检索文档 / 工具返回」留的空间（见第四节）
    """
    if reserve_output >= ctx_limit or system_tokens + reserve_output >= ctx_limit:
        raise ValueError(
            f"上下文预算已经赤字：limit={ctx_limit} system={system_tokens} out={reserve_output}"
        )
    budget = ctx_limit - system_tokens - reserve_output
    if budget <= reserve_retrieval:
        raise ValueError(
            f"历史预算非正：budget={budget} retrieval={reserve_retrieval}"
        )
    return {
        "history_budget": budget - reserve_retrieval,  # 滑窗可以吃掉的部分
        "reserve_retrieval": reserve_retrieval,
    }
```

两个细节值得单独说：

- **`reserve_output` 不是可选项。** 只按「输入放得下」算预算，模型答到一半会被 max_tokens 切断，
  表现出来就是回答莫名其妙断掉，而且很难和上下文问题联系起来。
- **必须写成断言。** 像上面那样，在真正裁剪之前先把「预算是否为正」算出来；
  负数不做处理的话，下游会拿到一个负预算的窗口，行为完全不可预测。

> **提示**
>
> 算出来的预算只用来**告警和排序**，不要当成硬性上限去卡。真实对话里 token 数没法精确预估
> —— 用户可能突然粘一整段日志。硬卡的结果是「明明还能聊，却被系统拒了」，体验比偶尔超一点差得多。

### 边界：滑动窗口滑到最后，可能一条都不剩

预算反推解决了「开多大」，但没解决「从哪开始滑」：**当前这一轮永远不能删。**

用户刚说的一句话，如果被自己的裁剪逻辑挤掉，模型会答非所问，而且它不知道自己漏了什么。
所以裁剪的终止条件不是「预算够了」，而是「**预算够了，并且至少留下了本轮**」。
这两句话在代码里长得差不多，行为差很远。

## 摘要：把更早的历史压成一段 {/* s3 */}

滑窗只能往前保真，滑出去的怎么办？直接丢掉会丢出问题。

我印象很深的一次：用户第一句说「我要退货，订单号 20260901001」，聊了七八轮之后问「**那个**什么时候能到账」。
滑动窗口早把第一句滑走了 —— 模型不知道「那个」指什么，只能反问「您说的是哪笔订单？」。
用户觉得这客服有点傻，其实是我们把记忆删了。

所以更早的历史要压成一段摘要，挂在窗口前面。但摘要不是随意的有损压缩，
**它得保留对后续轮次仍然有用的东西**：

- **待办状态**：用户要干嘛、进行到哪一步了？必须留，否则后面每轮都要重新问一遍。
- **稳定事实**：订单号、商品名、地址这类用户报过一次、后面不会再报的信息 —— 摘要里丢了就真丢了。
- **已排除项**：用户明确拒绝过的方案。不说清楚，模型会一次次把被否掉的方案重新提出来。

反过来，**过程细节可以丢**：中间查了哪些表、工具返回的原始 JSON，这些只在当轮有用。

### 摘要要异步做，不要卡在用户面前

第一版我是同步做的：超出窗口先调一次模型写摘要，再拼 prompt。结果是每次触发摘要的那一轮，
**首字延迟肉眼可见地翻倍** —— 用户就多打了一句话，凭什么要多等两三秒？

改成异步之后：这一轮先只用滑窗里的原文正常回答；摘要放到后台任务里，生成完写入会话状态，
**从下一轮开始生效**。代价是**有一段窗口是「没有摘要」的** —— 所以滑窗必须留够冗余，
软上限不能贴着预算算，否则异步摘要还没回来、窗口已经滑过头了，
那一段历史会同时「不在原文里」也「不在摘要里」，凭空消失。

> **注意**
>
> 滚动摘要还有个隐蔽的坑：**摘要会累积误差**。如果每轮都拿「旧摘要 + 新滑出的一轮」继续重写，
> 几十轮之后细节会逐渐模糊甚至漂移 —— 这是典型的压缩失真叠加。
>
> 更稳的做法是让摘要**有结构**（当前待办 / 关键事实 / 已排除项 / 其余），
> 并给摘要本身设长度上限；超了就按结构合并，不让它自由生长。

## 预算：先裁谁，后裁谁 {/* s4 */}

前两层管的是**对话历史**。但上下文里还有一大块东西不来自对话 ——
工具返回的 JSON、检索命中的长文档。它们有几个共同的麻烦：

- **长度不可控**：查一次订单日志，返回几十 KB 很正常。
- **当轮才需要**：这份 JSON 的价值基本只在这一轮，下一轮模型不会再关心。
- **但它占的是同一份预算**：不会因为「它是工具返回的」就免费。

所以必须规定一个**裁剪顺序**：

| 优先级 | 内容 | 处理方式 | 为什么 |
|---|---|---|---|
| 1 | system prompt + 工具 schema | 永不裁剪 | 裁掉模型就不知道怎么干活了 |
| 2 | 当前这轮 user 消息 | 永不裁剪 | 裁掉等于答非所问 |
| 3 | 最近几轮原文 | 按滑窗保留 | 保真的主力 |
| 4 | 当前轮的工具返回 / 检索文档 | 超限则截断，保留头部 + 尾部 | 当轮要用，但可以压缩 |
| 5 | 更早历史的摘要 | 超限则按结构再压 | 有损但保留骨架 |
| 6 | 最老的整组历史 | 优先删除 | 价值最低 |

顺序对应一个判断：**内容越新、越被当前问题直接依赖，就越晚被裁。**

### 大块内容要「截断」而不是「删除」

工具返回和检索文档在第 4 档，意味着它们**可以被压缩但通常不该被整条扔掉**。
整条扔掉会让模型以为「查了但没查到」，然后去重复调用同一个工具 —— 这比直接告诉它「返回太长，已截断」糟得多。
我自己的做法是**保头保尾**：

```python
def shrink_blob(text: str, limit: int) -> str:
    """保头保尾中间打标记；保证 len(结果) <= limit。"""
    if limit <= 0:
        return ''
    if len(text) <= limit:
        return text

    # 关键：标记里的字符数位数会变（22~26 字符），所以预留要按**最坏情况**算。
    # 这里按 removed 最多 9 位（十亿字符，远超任何现实输入）预留。
    RESERVE = len("\n... [已截断 999999999 字符] ...\n")   # = 28
    if limit <= RESERVE:
        # 位置不够放标记，退化成纯头部截断 —— 保留内容，不保留提示。
        return text[:limit]

    keep = limit - RESERVE                      # 保证 keep + 实际标记 <= limit
    head = (keep + 1) // 2
    tail = keep - head
    removed = len(text) - head - tail
    marker = f"\n... [已截断 {removed} 字符] ...\n"
    # ⚠️ tail 可能为 0，而 `text[-0:]` 在 Python 里是**整个字符串**，不是空串。
    # 必须显式判空，否则 limit 刚好比 RESERVE 大一点时会返回比原文还长的结果。
    head_part = text[:head]
    tail_part = text[-tail:] if tail > 0 else ''
    return head_part + marker + tail_part
```

改对之后有个反直觉的地方：`head + tail + len(marker)` 会比 `limit` **略小**几格
（预留按最坏情况算，实际标记通常更短）。这是故意的 ——
**宁可少放几个字符，也不要让截断后的结果悄悄超出预算。**

那个 `tail > 0` 的判断是我真实踩到的坑：`limit` 刚好比预留大一点时 `tail` 会是 0，
而 **`text[-0:]` 等于 `text[0:]`，返回的是整个字符串** —— 你以为在截断，实际把原文原样返回了。
这种错只在参数取特定整数时才触发，随便测两个大一点的数完全测不出来。

关键不在这个函数写得多好，而在于**截断必须显式**。给了标记，模型知道自己看到的是一部分，
要么用它现有的信息回答，要么换个参数再查一次；不给标记，它会瞎猜。

> **提示**
>
> 更彻底的做法是**在工具层就限制返回体积**，而不是等它进了上下文再裁。
> 工具描述里写清「最多返回 N 条」，比事后截断可靠得多 —— 前者是契约，后者是补救。

## 修法：分组感知裁剪 {/* s5 */}

现在回到第一节那个翻车现场。根因说穿了很简单：**裁剪的粒度选错了。**

「一问一答是一对」这个假设，在纯对话下等价于「一次用户交互」；一旦有了工具调用，两者就不再相等。
一个交互的最小单位应该是这样的**组**：

```text
组 = user
   | user + assistant(tool_calls) + tool… + assistant
```

也就是「一条 `user` 消息，加上它引发的所有后续消息，直到下一条 `user` 出现为止」。
按这个粒度裁剪，两个性质自动成立：

- 窗口**必然以 `user` 开头** —— 因为删除的单位就是整组，不会留下尾巴
- `assistant(tool_calls)` 和它对应的 `tool` 消息**永远在同一组里**，不可能被拆开

实现上不复杂，难的是把「预算」和「当前轮不可删」这两条同时满足：

```python
USER = "user"

def split_groups(messages: list[dict]) -> list[list[dict]]:
    """按 user 消息切组。不以 user 开头的消息（比如 system）单独成组放最前。"""
    groups: list[list[dict]] = []
    for msg in messages:
        if msg.get("role") == USER:
            groups.append([msg])
        elif groups:
            groups[-1].append(msg)   # 工具调用链跟在自己那组的 user 后面
        else:
            groups.append([msg])     # 开头的非 user 消息：各自成组
    return groups


def trim(messages: list[dict], budget_tokens: int, count_tokens) -> list[dict]:
    """按 token 预算裁剪，但以「组」为单位，且永不删除当前轮（最后一组）。"""
    groups = split_groups(messages)
    if not groups:
        return []

    # 从最后一组往前保留：last_idx 是窗口起点。
    # 注意：循环至少跑一轮（`last_idx < len(groups)` 这个条件），
    # 所以最后一组——当前轮——无论如何都进窗口。
    used = 0
    last_idx = len(groups)
    for i in range(len(groups) - 1, -1, -1):
        cost = sum(count_tokens(m) for m in groups[i])
        if used + cost > budget_tokens and last_idx < len(groups):
            break
        used += cost
        last_idx = i

    window = [m for g in groups[last_idx:] for m in g]

    # 质量兜底：预算极紧时窗口会滑到只剩当前轮一条 user 消息，
    # Agent 退化成完全没有记忆的玩具。这时**优先保住当前轮前面的那一组**，
    # 只有连它都留不下、窗口真的只剩一组时，才整段交回去让上游去判超限。
    if last_idx == len(groups) - 1 and len(groups) > 1:
        if used <= budget_tokens:          # 只剩一组是因为装不下，不是因为没钱
            return window
        return [m for g in groups for m in g]

    return window
```

有两处是刻意写成这样的：

- **`last_idx < len(groups)` 这个条件**：它保证循环至少跑一轮，也就是最后一组（当前轮）
  无论如何都进窗口。哪怕当前轮自己就超预算，也**不在这里删** —— 超预算该走的是
  「压缩当前轮的大块内容」，而不是把一个正在被回答的问题删掉。
- **质量兜底那一段**：一开始我写的是「只剩一组就整段塞回去」。第一版看着没问题，
  直到我拿一串递减的预算跑它 —— 预算从 30 降到 20 时，窗口反而从 3 条消息**涨回了全部 7 条**。
  这是个反向 bug：**预算收紧，窗口反而变大。** 修法是先判断「只剩一组」的原因
  是预算不够还是恰好装得下，只有真的装不下才回退整段。

兜底该不该有？留着一组看似浪费，但它保的是「不静默失忆」——
与其把对话阉割成一条没有记忆的 user 消息，不如诚实地让上游去报超限。
全丢是坏结果，但「看起来正常、实际失忆」是更坏的坏结果。

验证方式也值得说：我没有只测「对话能不能用」，而是**补了 8 个边界用例** ——
当前轮带工具调用、历史里连续多个工具调用、单组就超预算、空历史、
窗口正好卡在组边界、最后一条是 `tool` 结尾等等。另外还**拿预算从宽到窄扫一遍**，
确认窗口大小随预算单调不增 —— 那个反向 bug 就是这么抓出来的。
全量测试通过之后，重启服务实测多轮链路正常。

> **注意**
>
> 这类 bug 的教训不是「记得处理工具调用」，而是：**裁剪逻辑必须有自己的测试。**
> 它是个纯函数，最适合单测，却经常因为「就是个切片嘛」而完全没有覆盖。
> 我当时的测试全绿，因为没有任何一个用例里出现过工具调用。

## 顺带两件小事 {/* s6 */}

这两件事不属于三层策略本身，但会直接影响它的成本。

### 前缀缓存：让裁剪不出现在账单上

把 system prompt、工具 schema、摘要、滑窗原文按固定顺序拼成 messages，**前缀就是稳定的** ——
每轮只有尾部在长。这正好能吃上大多数模型服务的**前缀缓存**（prefix caching）：
命中缓存的输入单价明显更低，延迟也更低。反过来，每轮重新生成摘要、或者打乱工具 schema 的顺序，
前缀一直在变，缓存全部失效，每轮都按全价计费。

> **提示**
>
> 前缀缓存对裁剪策略有个隐性要求：**从头部裁剪**是安全的（前缀缩短，剩下的依然命中），
> 而**从中间编辑历史**会让后面所有内容全部缓存失效。
> 这也是「删除最老的组」比「重写中间的历史」更划算的原因之一。

### 会话状态放 Redis，带 TTL

历史得有个落脚点，否则下一次请求根本不知道聊过什么。我的做法是把会话上下文放 Redis，并设 TTL。
TTL 有两层意义：

- **成本与内存**：会话数据不需要永久保留，过期自动回收。
- **行为正确性**：TTL 一过，这个会话就是新会话 —— 不能出现「用户隔了一天回来，
  Agent 还记得上次的退货流程走到哪」。对客服场景来说，这是业务约束，不只是清理策略。

摘要和滑窗最好**存在同一份会话状态里**，一起读写、一起过期。分开存很容易出现
「摘要还在、原文没了」的错位状态，而错位状态下的裁剪行为是没法推理的。

## 小结 {/* s7 */}

- **滑窗**：窗口大小由预算反推，不是拍数字；当前轮永不删除，这是硬约束。
- **摘要**：留待办 / 事实 / 已排除项，丢过程细节；异步生成，接受「有一段窗口没有摘要」这个过渡态。
- **预算**：按「越新、越被当前问题依赖，越晚被裁」排序；大块内容**截断而不是删除**，且截断要有标记。
- **裁剪的单位是组，不是消息。** 按成对删除，一旦有工具调用就会把调用链剪断，
  窗口以 `tool` 开头，上游拒收 —— 而且之后每一轮都失败。静默、且持续失败。
- **裁剪逻辑是个纯函数，它值得自己的单元测试和边界用例。**
