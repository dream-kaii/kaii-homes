## 1. 目标与定位

### 1.1 一句话定位

> **一个 Java 后端工程师转型 Agent 应用开发的作品集站。用工程化的方式讲清楚「AI 怎么落地」。**

### 1.2 受众与转化目标

| 访客 | 关心什么 | 站点要给他的 |
|---|---|---|
| HR / 非技术 | 这人有没有东西、值不值得约面试 | 15 秒内看懂「他在做 AI 应用」+ 项目规模数字 |
| 技术面试官 | 深度够不够、有没有真踩过坑 | 工程细节、架构决策、踩坑记录 |
| 同行 | 有没有可复用的经验 | 技术文章 + 学习路线 |

**转化目标**：让访客产生「约他聊聊」的念头。

### 1.3 原站问题（已核实）

原站为 Hexo + Butterfly 主题，仅提交编译产物，存在以下问题：

1. **无源码**：仓库只有编译后的 HTML，改不动
2. **配置失效**：`CNAME` 仍指向过期域名；全站 canonical / og:url 都是 `http://example.com`
3. **导航 404**：`/music/`、`/movies/`、`/about/` 三个入口在仓库中无对应页面
4. **定位不符**：Butterfly 是生活博客主题，含看板娘、访客统计等，与求职场景不匹配
5. **内容埋雷**：生活随笔《四月的第一天》记录实习受挫情绪，作为求职入口是减分项

## 3. 设计系统

### 3.1 配色（从用户素材采样）

主色取自用户提供的手绘背景图 `index-my.png`，实测采样结果：

| 色值 | 占比 | 用途 |
|---|---|---|
| `#B5CA4D` | 32.4% | 强调色 / 高亮 |
| `#467A4A` | 30.0% | 主色（深绿） |
| `#AAC74C` | 19.2% | 辅助 |
| `#3B5B32` | 3.8% | 标题文字 |

最终设计令牌（`design-mockup/*.html` 的 `:root`）：

```css
--paper:#FAF9F2     /* 页面底色：暖白纸感 */
--card:#FFFFFF      /* 卡片 */
--paper2:#F2F1E4    /* 次级背景 */
--gh:#B5CA4D        /* highlight 亮绿 */
--gm:#5E8A4E        /* mid 中绿 */
--gd:#3E6B3F        /* deep 主色 */
--gk:#2A4D2E        /* dark 深色（按钮） */
--ink:#1F2919       /* 主文字（带绿相的近黑） */
--ink2:#48543E      /* 正文 */
--ink3:#7A8570      /* 次要 */
--ink4:#A6AE9C      /* 标注 */
--line:#E2E1D2      /* 边框 */
```

**为什么不用深色科技风**：初版设计稿曾用「深蓝黑底 + 霓虹强调色 + 等宽字体」的暗色科技风，实测观感「一眼 AI 生成」。该风格被 `web-artifact-designer` 技能的反模式清单明确列为 AI 味最重的套路之一。改为从用户自有素材推导配色后，站点具备了不可替代的辨识度。

### 3.2 字体

- 正文：系统无衬线栈（`PingFang SC` / `Microsoft YaHei`）
- 等宽：仅用于**数字、日期、技术标签、代码**（传达技术感，不滥用）
- 中文字体不做 Web 字体引入（体积原因）

### 3.3 间距与圆角

- 间距刻度：`4 / 8 / 16 / 24 / 32 / 48 / 64 / 96`
- 圆角：`8 / 14 / 22`（分别用于小元素 / 卡片 / 大容器）

### 3.4 动效原则

**每一处动效都必须在说明结构，而非纯装饰**。统一时长 220–750ms。

| 动效 | 位置 | 说明什么 |
|---|---|---|
| 滚动入场（`IntersectionObserver` 分级延迟） | 全站区块 | 内容层级 |
| 数字滚动计数 | 项目指标 | 数据量级 |
| Hero 视差 + 光标光晕 | 首页首屏 | 空间纵深 |
| 荧光笔高亮展开 | Hero 标题 | 强调重点 |
| 思考链转圈→打勾 | 首页同步演示 | 思考过程 |
| 运行状态指示（播放中/完成） | 首页演示条 | 进度 |
| 时间轴进度线填充 | 十步演进 | 阶段推进 |
| 复制反馈 | 代码块 | 交互确认 |

**全局约束**：所有动效包裹在 `@media (prefers-reduced-motion: reduce)` 中，用户系统开启减少动效时全部关闭。

## 4. 页面设计

### 4.0 统一的三栏骨架

除首页外，所有内容页采用同一套三栏布局，**左右栏职责互不重叠**：

```
┌──────────┬─────────────────┬──────────┐
│  212px   │   740px 正文     │  236px   │
│ 信息/导航 │                 │ 目录/延伸 │
└──────────┴─────────────────┴──────────┘
```

| 页面 | 左栏 | 右栏 |
|---|---|---|
| 文章详情 | 阅读进度环 · 本文信息（发布/阅读/字数/分类）· 标签 · 操作 · **系列文章** | **本文目录**（唯一一份）· 相关文章 |
| 项目详情 | 进度环 · 项目信息 · 技术栈标签 · 操作 · 其他项目 | 本页目录 · **关键数据** · 按阶段跳转 |
| 文章列表 | **分类筛选器**（可点）· 文章统计 · 热门标签 | 推荐阅读 · 写作计划 · 按主题浏览 |
| 学习路线 | 进度环 · 路线概览 · 文章状态 · **路线切换器** | 当前路线目录（随 Tab 切换）· 文章进度 · 相关文章 |
| 关于 | 基本情况 · 关键词 · 操作 · 快速跳转 | 本页目录 · 现在在做什么 · 作品入口 |

**响应式收缩**：`< 1320px` 收右栏 → `< 1080px` 收左栏 → 正文居中，`< 700px` 边距收窄至 16px。

**首页例外**：Hero 采用左右分屏（左文案 / 右技术名片），首屏需要更强的视觉冲击力，不套三栏。

### 4.1 首页（`index-v9.html`）

**结构**：

```
① Hero            自我介绍（左：文案+头像+社交 / 右：技术名片）
② HOW IT WORKS    Agent 与普通 AI 对比同步演示
③ LANDSCAPE       一个 Agent 应用要做好哪些事（三栏）
④ EVOLUTION       Agent 应用的十步演进（可交互时间轴）
⑤ PROJECTS        三个项目卡
⑥ WRITING         技术文章（8 篇，与文章列表页标题完全一致）
⑦ GLOSSARY        名词速查（折叠，12 条）
⑧ CONTACT         联系
```

**关键设计决策**：

1. **Hero 用左右分屏，不是产品落地页**。依据：`empire-ui.com`《Portfolio Hero Section Designs》指出「开发者作品集最常见的失败是居中的 Hi I'm XXX」，且「Hero 的任务不是解释你，而是让人想继续了解你」。左半对人，右半对工程师。

2. **右侧技术名片**承担三件事：展示头像、说清定位、用 `Agent / Java` 两格暗示方向。原设计曾在此放规模数字（10/6727/48），后改为方向标签 —— 头像卡上堆数字像简历轰炸。

3. **对比演示（区块②）承担「让不懂的人也看懂」**。不写科普段落（会让技术面试官觉得被小看），而用左右并排动画让人直观感受：
   - 左：普通 AI —— 2 步结束，说「我查不到」
   - 右：Agent —— 5 步思考 + 5 个系统环节同步点亮，最后给出答案
   - 节奏 1050ms/步，Agent 从 2.3s 开始，总时长约 7.6s
   - 思考链圆圈先「转圈」（780ms/圈），620ms 后变「打勾」并点亮连接线
   - 支持「重播」，进入视口自动播放一次

4. **十步演进时间轴不带项目名**。用通识技术演进讲领域认知，具体项目在项目页展开。每步右栏写「容易踩在哪儿」，内容源自真实踩坑的抽象化。

5. **名词速查折叠面板**（区块⑦）+ 正文 6 处术语悬停解释，解决「访客可能不知道 Agent 是什么」而不占篇幅。

### 4.2 项目详情页（`project-detail-v2.html`）

以 MewHelp 为例，统一结构：

```
01 这个项目做了什么
02 架构是怎么一步步长出来的（十章演进卡）
03 我解决过的工程问题（★ 核心）
04 一段关键实现（带高亮的代码块）
05 已知限制
```

**区块 03 是全站最有价值的部分**。每个案例统一五段式：**问题 → 后果 → 定位 → 方案 → 验证/取舍**。

四个案例（均源自项目真实开发记录）：

| 案例 | 严重度 | 摘要 |
|---|---|---|
| 上下文裁剪把工具调用链拆散 | CRITICAL | 按「对话对」裁剪在含工具调用的会话中失效，导致后续每轮请求被上游拒收 |
| 工具超时取消不了同步调用 | IMPORTANT | `asyncio.wait_for` 无法取消线程中的同步工具，副作用操作被重试两次 |
| 嵌入模型每轮重建 | IMPORTANT | 每轮请求重载数 GB 权重 + 连接泄漏，首个知识类问题超时 |
| 测试替身把 bug 藏起来 | IMPORTANT | 替身比真实实现更宽容，测试全绿但线上必崩 |

**区块 05「已知限制」刻意保留**：主动写清边界比声称「完美」更专业。

### 4.3 文章页（`article-mockup.html` + `writing-index-mockup.html`）

**列表页**：左侧分类筛选（全部/Agent/Java/算法），Agent 优先排序；右侧推荐阅读 + 写作计划。

**详情页**：

- 正文 740px，左右栏各司其职（见 §4.0）
- **交互式组件**：如 RAG 文章的「召回结果对比器」，可切换关键词/向量/混合三种模式，动态展示召回结果和分数条动画
- 代码块带语言标签、复制按钮、行高亮
- **参考来源区块**（编号 + 链接 + 类型标签）
- 作者卡 + 上下篇导航

**写作纪律**（重要）：

1. 凡引用必附来源，给出可点击链接
2. 不编造版本号、API 签名、性能数字
3. 版本敏感 API 先查官方文档再落笔
4. 讲「为什么这样设计」和「踩到什么坑」，不罗列名词

### 4.4 学习路线页（`learning-path-mockup.html`）

三条线用 Tab 切换，**每一步链到自己的文章**（不链官方文档）：

```
┌─ 03 让模型会调工具                          3-5 天 ─┐
│  Function Calling 是 Agent 的分水岭……                │
│  ────────────────────────────────────────            │
│  [已有] 工具调用的三个工程问题：超时、幂等与重试边界 →  │
│  文档  LangChain · Tools ↗   Agents ↗                 │
└──────────────────────────────────────────────────────┘
```

- `[已有]` 绿标 = 文章已完成，可点
- `[待写]` 灰标 = 已规划，未动笔
- 官方文档降级为底部一行小字，不单独占一步

**Agent 线（7 步）**：先读概念 → 把一次对话调通（**先不用框架**）→ 让模型会调工具 → 接上知识（RAG）→ 图编排焊死流程 → 接外部工具生态（MCP）→ 让它能被运维

**算法线（6 步）**：先建地图 → Hash → 双指针/滑窗 → 链表 → 树与图 → **DP 放最后**

**后端线（6 步，按用户指定顺序）**：

```
STEP 01  语言基础        Java 语法、集合、面向对象
STEP 02  MySQL          SQL、索引、事务
STEP 03  框架           Spring / SpringBoot / MyBatis
STEP 04  Redis          数据结构、缓存、并发
STEP 05  分布式与中间件   MQ、分布式锁、微服务
STEP 06  JVM 与深度      内存结构、GC、并发原理
```

概览里解释了为什么 JVM 放最后：「它解释的是前面这些为什么会有性能问题 —— 没有前面的实践，硬啃内存模型和 GC 只会变成背结论」。

## 5. 技术方案

```
Astro 5 + Tailwind CSS 4
├── 内容：Markdown / MDX（Content Collections + Zod 类型校验）
├── 交互：Astro Islands（仅在需要处水合）
├── 主题：亮色为主
├── 搜索：Pagefind（纯静态索引）
├── SEO：sitemap + RSS + 结构化数据 + OG 图
├── 部署：GitHub Pages + GitHub Actions
└── 域名：待用户提供，配置 CNAME
```

**为什么对简历有利**（站点本身即第 4 个项目）：

- Astro Islands 零 JS 默认 → 可讲「内容站不需要客户端框架」
- Content Collections + Zod → 可讲「内容即数据，构建时类型校验」
- GitHub Actions → 可讲自动化部署
- Lighthouse 满分 → 可拿出可量化指标

**待修复的历史遗留**：canonical / og:url 不能再是 `example.com`；CNAME 用新域名。

**从设计稿到 Astro 的映射**：

| 设计稿 | Astro 实现 |
|---|---|
| 三栏骨架（6 个页面重复） | `layouts/BaseLayout.astro` + `layouts/ContentLayout.astro` |
| 左右栏内容 | 各页面通过 slot / props 注入 |
| 文章 | `src/content/writing/*.md`（Content Collections + Zod） |
| 项目 | `src/content/projects/*.md` |
| 学习路线步骤 | `src/content/learning/**` 或数据文件 |
| 交互组件（召回对比器、时间轴、对比演示） | `src/components/*.astro`（Islands，按需水合） |

## 8. 验收标准

1. 首页在 375 / 390 / 768 / 1440 四个尺寸下无横向溢出
2. 全部动效尊重 `prefers-reduced-motion`
3. 页面自包含可离线打开（设计稿阶段），生产环境资源走构建流程
4. 内链无 404，外链可访问
5. 所有引用有来源，所有数字可追溯
6. Lighthouse 桌面端 ≥ 95 分（性能 / 可访问性 / 最佳实践 / SEO）
