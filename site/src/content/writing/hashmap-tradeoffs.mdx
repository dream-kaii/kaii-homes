## 从一次「哈希没生效」说起 {/* s1 */}

我接手过一个内部服务，接口的 P99 偶尔从 8ms 跳到 200ms 以上，复现不出来，重启就好了。压测时打出这么一行：

```
不扰动：占用 1 个桶，最长链表 32
```

那是一批编号递增的 key，hashCode 长得像 `0x00010000`、`0x00020000` —— 低 16 位**全是 0**。而容量 16 的表定位桶靠 `hash & (16 - 1)`，只取最低 4 位，于是 32 个 key 全挤在一个桶里。查询从 O(1) 退化成 O(n)。同一次运行，换成数值会散开的 key：

```
不扰动：占用 1 个桶，最长链表 32
扰动后：占用 16 个桶，最长链表 2
```

那次排查之后我把 `HashMap` 的源码翻了一遍。最大的感受是：里面那些看起来像"魔法常数"的东西 —— 16、0.75、8、6、64 —— **每一个都在回答同一个问题：时间、空间和哈希冲突，这三者该怎么分账。**

这篇是[Java 后端路线](/learning-path/)「语言基础」那一课。面试最爱问这一段，但背结论没用，所以下面每个决策我都换一个角度问：**如果不这么设计，会付出什么代价。**

## 数组 + 链表 + 红黑树：三种结构各管一段 {/* s2 */}

### 数组解决"定位"，链表解决"共存"

骨架必须是数组，因为只有数组能提供 **O(1) 的随机访问** —— 下标算出来是几就直接跳到第几个槽位。哈希计算是常数时间，`hash & (n-1)` 是常数时间，剩下那次内存访问就是数组寻址。

但数组有个硬伤：**槽位有限，key 空间无限。** 不同的 key 算出同一下标 —— 哈希冲突 —— 在数学上不可避免。容量 16 的数组装 3 个元素，冲突概率就超过 17%。所以需要第二层结构容纳"撞在同一个桶里的元素"，JDK 早期用的是链表：

```java
// JDK 8 的 Node：每个桶挂一条单链表
static class Node<K, V> implements Map.Entry<K, V> {
    final int hash;
    final K key;
    V value;
    Node<K, V> next;   // 指向桶里下一个节点
}
```

查找时先定位桶，再顺着 `next` 逐个比对 `hash` 和 `equals` —— 为什么两个都要比？因为 `hash` 只是 32 位整数，不相等的对象完全可能哈希碰撞；`equals` 才是最终答案，而先比 `hash` 是为了用一次整数比较省掉一次可能很贵的 `equals` 调用。

链表的代价很清楚：**冲突越多链表越长，查找越接近 O(n)。** 这叫"哈希退化"—— 结构没变，时间复杂度偷偷掉了一个数量级。开头那次 P99 抖动，退化的就是这一层。

### 红黑树是给最坏情况买的保险

JDK 8 引入红黑树，把长链表的 O(n) 遍历换成 O(log n) 的树查找。

> **提示**
>
> 树化不是把整条链表"变"成一棵树，而是**在原桶位置换成了 `TreeNode`**。`TreeNode` 继承自 `LinkedHashMap.Entry`，既是树节点又保留了 `next` 指针 —— 所以 JDK 8 的桶是"树 + 链表"的混合体，树化了也能按原顺序遍历过去，这是 `LinkedHashMap` 在 JDK 8 之后依然能保序的关键。

### 8 和 6 为什么是两个数，不是一个

先说 8 怎么来的 —— 它来自泊松分布。理想随机哈希下，一个桶里落进 `k` 个元素的概率满足 λ = 0.5 的泊松分布：

| k | 概率 | 换算成"多少分之一" |
| --- | --- | --- |
| 4 | 0.0015795069 | 1/633 |
| 6 | 0.0000131626 | 1/75973 |
| 7 | 0.0000009402 | 1/1063623 |
| 8 | 0.0000000588 | 1/17017969 |

这就是 JDK 源码注释里那张表的原意：**链表长度到 8 的概率约千万分之六（1/1700 万）。** 也就是说，树化这个机制正常情况下一辈子都用不上。

那为什么还要写？因为"正常情况"是个强假设 —— 它要求 `hashCode` 分布足够均匀。一旦 key 的 hashCode 被人为构造（比如写成 `return id % 100;`），或者本身有系统性偏差（比如开头那批低 16 位全 0 的编号），随机性假设就崩了。**红黑树不是为平均情况准备的，它是为"哈希函数失效"准备的兜底。**

那 6 呢？**7 和 8 之间那段空档，是一个防抖缓冲区。** 如果只设一条线（比如 7），某个桶恰好挂 7 个元素时，加一个就树化、删一个就退化；业务代码在插入删除之间高频抖动，桶就会在链表和树之间反复切换 —— 每次切换都要重构节点，代价远大于多挂一个链表节点。设两条线，**只有"明显变糟"才升级、"明显变好"才降级**，中间的空档吸收掉抖动。

这个模式在系统设计里很常见：GC 的分代晋升、TCP 的拥塞窗口、限流器的恢复速率 —— 凡是"状态切换有成本"的地方，单阈值都会抖，双阈值才能稳。

### 还有两个常被漏掉的边界：64 和 untreeify()

树化还有一道前置门槛：**只有整个表的容量达到 `MIN_TREEIFY_CAPACITY`（64）时才真的树化。**

```java
final void treeifyBin(Node<K, V>[] tab, int hash) {
    int n, index;
    Node<K, V> e;
    if (tab == null || (n = tab.length) < MIN_TREEIFY_CAPACITY)
        // 没到 64，只扩容不树化
        resize();
    else if ((e = tab[index = (n - 1) & hash]) != null) {
        // ... 真正把链表转成红黑树
    }
}
```

这个判断值得琢磨。容量还小（16、32）而某个桶已挂了 8 个节点，**大概率不是哈希函数有问题，而是表太小** —— 桶数不够分。正解是扩容，把桶数翻倍重新分配，冲突自然散了；上红黑树属于用重武器处理一个容量问题。

还有第三个反向检查：**树节点少于 6 个时主动 `untreeify()` 拆回链表。** "树"这个形态是有主动退场的，只在能覆盖自身开销时才保留。几条判断合起来，取向一致：**红黑树是例外路径，链表才是默认路径。**

| 结构 | 定位成本 | 冲突时的查找 | 额外空间 | 什么时候是主角 |
| --- | --- | --- | --- | --- |
| 数组 | O(1) | —— | 极低 | 定位 |
| 链表 | 依赖数组 | O(k)，k 为桶内长度 | 每个节点一个 `next` | 冲突少（默认） |
| 红黑树 | 依赖数组 | O(log k) | 每个 `TreeNode` 多约一倍字段 | 冲突严重（兜底） |

## 为什么扩容是翻倍：一次位运算和一条「二选一」 {/* s3 */}

### `(n - 1) & hash` 不是取模的缩写

定位桶最朴素的写法是取模 `hash % n`。JDK 用的是 `hash & (n - 1)`，两者在 **n 是 2 的幂**时完全等价：

```
n=16  n-1=15  01111
n=32  n-1=31  11111
```

15 是 `01111`，31 是 `11111` —— 低位连续一串 1，所以 `hash & 15` 的结果恰好落在 `[0, 15]`，和 `hash % 16` 一样。一旦 n 不是 2 的幂，等价立刻失效：

```
n=48  n-1=47  101111   ← 有一个 0 位被"吃掉"了
```

47 的二进制第 4 位是 0，所有在这位上为 1 的 hash 都会落进同一个桶，一半桶位被浪费。**所以"容量必须是 2 的幂"不是审美偏好，它是位运算能替代取模的前提条件。**

那为什么非要换掉取模？

1. **速度快。** 位与是一条 CPU 指令；`%` 在除数是变量时是真实除法，x86 上要几十个时钟周期。
2. **负数友好。** Java 里 `%` 对负数返回负值 —— `-5 % 16 == -5`，直接当数组下标会抛 `ArrayIndexOutOfBoundsException`；`&` 无论如何都得到非负结果。

> **注意**
>
> `HashMap` 里还有个和 `0x7fffffff`（源码里的 `HASH_BITS`）按位与的操作。
> 源码注释写明它的理由是"**把最高位也纳入计算**"，而不是防负数 —— 因为 `& (n-1)` 本身已经保证非负了。
> 这类细节只看代码推不出来，必须读注释。

### 扰动函数：把高位「折」进低位

只有低位参与运算，就直接带来一个问题：**hash 的高 16 位被完全忽略了。**

这在实践中很致命，因为很多 `hashCode()` 恰好只在高位作区别。比如把 id 乘 65536 的实现，所有 key 低 16 位都是 0 —— 容量 16 时全落 0 号桶，容量 32 时还是全落 0 号桶，扩容都救不了。JDK 的解法是在 `hash()` 里做一次扰动：

```java
static final int hash(Object key) {
    int h;
    // 把 hashCode 无符号右移 16 位后与自身异或：让高位也参与低位结果的计算
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}
```

`>>> 16` 把高 16 位搬到低位再异或一次。异或的性质是"该位是 1 就翻转、是 0 就保留"，于是**新的低 16 位同时包含了原低位和原高位的信息**，而高位本身不变。上面那批 key 跑出来是这样：

```
key=0x00010000  raw&15= 0  spread=0x00010001  spread&15= 1
key=0x00020000  raw&15= 0  spread=0x00020002  spread&15= 2
key=0x00030000  raw&15= 0  spread=0x00030003  spread&15= 3
key=0x00040000  raw&15= 0  spread=0x00040004  spread&15= 4
```

不扰动时四个 key 全在 0 号桶，扰动后分别落到 1、2、3、4 号桶。

> **提示**
>
> JDK 8 的扰动函数比 JDK 7 简单很多。JDK 7 用的是
> `h ^= (h >>> 20) ^ (h >>> 12); return h ^ (h >>> 7) ^ (h >>> 4);`，四次移位四次异或。
> 能砍到一次，是因为 JDK 8 引入了红黑树：**即使扰动不理想、某些桶退化成长链表，
> 树也能把最坏查找压回 O(log n)。** 有了兜底，"优化平均情况"就不再是必须的了。

### 扩容最巧妙的地方：元素只有两个去处

假设容量 16，元素下标是 `hash & 15`；扩容到 32 后是 `hash & 31`。**这两个结果有关系吗？**

有，而且极其简单。31 是 5 个 1，15 是 4 个 1 —— 31 比 15 多的那一位是第 4 位（`10000`，也就是 16）。所以：

- hash 第 4 位是 **0**：`hash & 31` 和 `hash & 15` **完全相同**；
- hash 第 4 位是 **1**：`hash & 31` 恰好等于 `hash & 15` **加上 16**。

**没有第三种可能。** 32 位 hash 里其余 27 位对下标的影响在新旧容量下是同一个，会被抵消掉。唯一决定去留的，就是扩容多出来的那一位。拿 `0..63` 这 64 个 hash 实算一遍：

```
0..63 这 64 个 hash 中：留在原位 32 个，移到原位+16 32 个
```

这条性质的价值，要对比"如果扩容不是 2 倍"才看得清。

**假设按 1.5 倍扩容**：容量 16 → 24，掩码从 `01111` 变成 `10111`。23 的二进制里有 0 位，原来的位与逻辑被打乱，每个元素的落点彻底重排 —— **每个元素都得重算完整下标，没有一个能留在原位。**

**而 2 倍扩容下，迁移不需要重算哈希** —— 源码注释写得很清楚：

```java
// 不需要重新计算 hash，只需要检查 hash 在原容量掩码之外的那一位 ——
// 那一位是 0 就留在原下标，是 1 就变成原下标 + oldCap
if ((e.hash & oldCap) == 0) {
    // 低位链：留在原位置
    loTail.next = e;
    loTail = e;
} else {
    // 高位链：移动到 原位置 + oldCap
    hiTail.next = e;
    hiTail = e;
}
```

`e.hash & oldCap` 里 `oldCap` 是 16（`10000`），只有第 4 位是 1 —— 这个表达式**取出来的正是"扩容多出来的那一位"**。等于 0 进低位链，否则进高位链。整个迁移把一个桶拆成两条链：一条原地不动，另一条整体平移到"原位 + oldCap"。

而且它是**原地拆链，不重算哈希、不重建节点**：只需要判断一个位、改两个尾指针。扩容这个"最贵的操作"，被一次位判断拆开了。

> **注意**
>
> 2 倍扩容是权衡后的选择，不是免费的午餐。它省掉迁移时的重算成本，代价是**内存分配粒度粗**：
> 从 16 直接跳到 32，实际只用到 20 个槽位的话，多出那份就是白占的。
> 另外容量只能是 2 的幂，所以 `new HashMap<>(1000)` 实际拿到 1024 ——
> 构造函数里的 `tableSizeFor()` 做的就是"向上取到最近的 2 的幂"。

## 负载因子 0.75：一个被算出来的数 {/* s4 */}

### 它到底在调节什么

负载因子（load factor）的定义是 `size / capacity`，它调节的是**空间和冲突之间的兑换比率**。

两个方向的极端都不可取：

**如果是 1.0**（存满了才扩容）：空间利用率最高，一个字节不浪费。但表最满时每个桶平均挂着 1 个元素，冲突概率显著上升，长链出现得更频繁 —— 只要哈希分布稍有不均，某些桶就会拖出长链，平均查找成本逼近 O(n)。这是"空间换时间"里省钱的那一端，省下的空间是用查询效率买的。

**如果是 0.1**（稍微存点东西就扩容）：冲突极少，几乎每个桶最多一个元素，查找稳定在 O(1)。但表里 90% 的槽位是空的；更糟的是**扩容极其频繁** —— 容量 16 的表存 1 个元素就扩到 32，存 3 个扩到 64，每次都要把已有元素全部迁移一遍，均摊成本非常可观。

0.75 是这条曲线上的折中点：**大多数桶是空的或只有一个元素，同时表里 3/4 的槽位被用上。** 这里要小心一个循环论证的陷阱 —— 泊松表用的是理想随机哈希，而真实世界的 hashCode 经常不理想。那张表描述的是"如果哈希函数够好会发生什么"，不是"你的业务代码会发生什么"。开头那批低 16 位全 0 的 key 身上，λ = 0.5 这个假设从一开始就不成立。**这正是 HashMap 还需要扰动函数、红黑树和 64 门槛的原因：三者都在给"哈希不理想"补位。**

验证方向可以自己量化：**把负载因子调成 0.4 跑一遍压测**。如果耗时明显下降，说明你的场景冲突确实严重；如果耗时没变、只有内存涨了，说明方向选错了 —— 用两倍多的内存什么也没换来。

> **提示**
>
> 负载因子可以被构造方法覆盖（`new HashMap<>(16, 0.5f)`），但这类调参对绝大多数业务没有价值。
> 真正值得做的是**创建时给出合理的初始容量**：确定要存 1000 个元素就直接 `new HashMap<>(2048)`，
> 省掉十几次扩容。这比调负载因子的收益大得多，也更容易验证。

## 这四个决策，其实是一件事 {/* s5 */}

并排看，四个问题问的是同一件事的不同侧面：

| 决策 | 换到了什么 | 付出的代价 |
| --- | --- | --- |
| 数组 + 链表 | O(1) 定位 + 容纳冲突 | 冲突多时退化成 O(n) |
| 链表 → 红黑树 | 最坏情况 O(log n) | 节点结构变重、树化/退化有切换成本 |
| 容量取 2 的幂 | 位运算替代取模，迁移只判断一位 | 空间分配粒度粗，容量只能翻倍 |
| 负载因子 0.75 | 冲突概率与空间利用率的折中 | 比 1.0 多用约 33% 的空间 |

它们都服务于同一个目标：**在不完美的哈希函数之上，把平均查找成本稳稳压在 O(1) 附近。** 拿掉任何一条，这个承诺都会在某种输入下失效。

## 一个容易被忽略的点：JDK 8 前后的插入方式 {/* s6 */}

前面讲扩容时提到的"低位链 / 高位链"是 JDK 8 的写法。JDK 7 是**头插法**：新节点插到链表头部：

```java
// JDK 7 的 transfer()：遍历旧表，把每个节点插到新桶的头部
while (null != e) {
    Entry<K, V> next = e.next;   // ① 先存下后继
    int i = indexFor(e.hash, newCapacity);
    e.next = newTable[i];        // ② 新节点的 next 指向新桶当前的头
    newTable[i] = e;             // ③ 新节点成为桶的新头
    e = next;
}
```

单线程下头插尾插都正确，只是遍历顺序相反。但头插法**会反转原链表的顺序**，这在并发扩容下会出人命：`e.next = newTable[i]` 这一步会**改写节点之间的指向关系**，而另一个线程可能正握着这个节点的引用往前走。两个线程的迁移进度交错时，就可能形成 `A.next = B` 且 `B.next = A` 的环。

一旦成环，后果是**读操作死循环**：每次 `next` 都走回自己，线程永远出不来，CPU 打满。现场表现是接口全部卡住、进程 CPU 100%、栈里全是 `HashMap.get`。这类问题不报错、不打日志，只能靠 `jstack` 的线程栈去认。

> **注意**
>
> 必须说清楚：**这不是"JDK 8 修复了 HashMap 的线程安全问题"。**
> 并发扩容的根因是**没有任何同步** —— 没有锁、没有 CAS、没有 volatile，
> 多线程对同一份 `table` 读写本来就是数据竞争。JDK 8 只是让这个**已经坏掉的结果更不容易变成环**：
> 尾插法保持了原有相对顺序，成环概率下降，但**丢数据、读到错误值、size 计数错乱依旧会发生。**
> 要并发就用 [`ConcurrentHashMap`](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/ConcurrentHashMap.html)
> 或 `Collections.synchronizedMap()`。HashMap 的单线程假设从来没有被放松过。

## 最后：这篇为什么值得花时间 {/* s7 */}

讲句实在的：**真实项目里我几乎没有直接调过 HashMap 的底层。** 城觅的秒杀链路用的是 Redis 原子操作和 Lua 脚本，智学云课堂里用 BitMap 做签到、ZSet 做排行榜、Caffeine 做本地缓存 —— 都是更高层的抽象。集合框架是面试高频，但不是"日常写业务必须天天用"的东西。

那为什么值一篇的篇幅？因为它是 Java 后端这条路上**第一次让你完整看到"一个工业级数据结构是怎么被权衡出来的"**。读 Redis 的 `dict` 为什么用渐进式 rehash、读 MySQL 的 B+ 树为什么扇出做得那么宽、读 JVM 的分代为什么是 1:2 —— 都是同一套思路。

所以我给这一课定的检验标准不是"能背出 16 和 0.75"，而是：**给你一个新的设计题（比如"给秒杀场景设计一个限流器"），你能不能说出每个参数在兑换什么、放弃什么。** 能答上来，这一课就过了。

## 小结 {/* s8 */}

- **数组 + 链表 + 红黑树是三段分工**：数组给 O(1) 定位，链表容纳冲突，红黑树给最坏情况兜底。默认路径是链表，树是例外。
- **树化阈值 8 来自泊松分布**：λ = 0.5 时链表长度到 8 的概率约 1/1700 万 —— 它是为"哈希函数失效"准备的，不是为平均情况。
- **8 和 6 之间的空档是防抖缓冲区**，避免桶在链表和树之间反复切换；**64 是树化门槛**，容量太小时正解是扩容而不是树化。
- **容量必须是 2 的幂，是位运算替代取模的前提**：`(n-1) & hash` 只有在 n 是 2 的幂时等价于取模，且天然对负数安全。
- **扰动函数 `(h = key.hashCode()) ^ (h >>> 16)` 把高位折进低位**，否则只有低位参与桶定位，高位信息全丢。
- **2 倍扩容最巧妙的地方是元素只有两个去处**：`e.hash & oldCap` 判断扩容多出来的那一位 —— 是 0 留在原位，是 1 移到原位 + oldCap。扩容不重算哈希。
- **负载因子 0.75 是空间与冲突的折中**，调大冲突多、查询慢，调小频繁扩容、浪费空间。真正值得做的是**创建时给出合理的初始容量**。
- **JDK 8 把头插法改成尾插法**，降低了并发扩容形成环形链表（进而 `get()` 死循环）的概率 —— **但这是"更不容易坏"，不是"修好了"。** 并发场景请用 `ConcurrentHashMap`。
