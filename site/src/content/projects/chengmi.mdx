## 这个项目做了什么

城觅是一个本地生活服务平台：商户、优惠券、秒杀、订单。业务本身不新鲜，
我想练的是**秒杀那条链路上的并发问题**，以及后来加上去的智能客服模块。

这条链路我改了四轮，每一轮都因为上一轮压不住才存在：

1. **阻塞队列** —— 单机内存队列削峰，服务重启就丢，多实例也不共享。
2. **Lua 原子扣减** —— 把「查库存 → 判断 → 扣减」压成一段 Lua 脚本，在 Redis 里原子执行，超卖没了。
3. **Redisson 分布式锁** —— 多实例下同一用户重复下单互相踩，用锁把用户维度串起来。
4. **Kafka 异步削峰** —— 同步落库扛不住瞬时流量，改成本地消息表 + Kafka 异步消费，并处理消费幂等。

## 我解决过的工程问题

<CaseCard severity="critical" title="AI 直接调写操作：模型说「帮你退了」，其实没退">
  <Fragment slot="problem">客服模块最初让模型直接调工具，包括取消订单、申请退款这类写操作。</Fragment>
  <Fragment slot="impact">模型会在用户只是抱怨时提前发起写操作，也会在参数缺失时编一个订单号。<b>对话里说「已为你取消」，数据库里订单还在。</b>这比答不出来严重得多。</Fragment>
  <Fragment slot="fix">定下<b>「AI 提议，用户确认，系统执行」</b>三段式：模型只能生成一个待确认的意图对象，前端渲染成可点的确认卡，用户点了才走既有服务方法。</Fragment>
  <Fragment slot="tradeoff">为什么不让模型自己判断该不该确认？因为「该不该动数据」是权限问题，不是语义问题，不能交给概率模型决定。</Fragment>
</CaseCard>

<CaseCard severity="important" title="客服模块一行表都没加，却要读写交易库">
  <Fragment slot="problem">最省事的做法是给 Agent 建几张会话表、工具日志表。但这样它就成了一个需要独立运维的子系统。</Fragment>
  <Fragment slot="fix">约束自己<b>不新增任何数据库表</b>：会话上下文放 Redis 带 TTL，工具调用复用已有的服务方法与消息链路，审计落到现有日志管线。</Fragment>
  <Fragment slot="verify">最终交付时 <code>git diff --stat</code> 里 0 张新增表的 DDL；Agent 模块 1849 行代码全在既有结构内。</Fragment>
</CaseCard>

<CaseCard severity="important" title="消息消费重试，同一笔订单扣了两次库存">
  <Fragment slot="problem">Kafka 消费端异常会重试，但下单消息的重试不是「重放」，是<b>再执行一遍业务</b>。</Fragment>
  <Fragment slot="impact">用户看到一次下单，库存掉了 2。这类问题只在流量起来时才暴露，本地单线程测永远测不到。</Fragment>
  <Fragment slot="fix">消费端按<b>业务幂等键</b>（用户 + 优惠券 + 时间片）落库前查重，重复消息直接 ack 丢弃，而不是依赖 at-least-once 语义蒙混过关。</Fragment>
</CaseCard>

## 一段关键实现

秒杀扣减的 Lua 脚本：把「查库存、判断是否已售罄、扣减」压进一次 Redis 原子执行。

```lua
-- seckill.lua —— 单脚本内完成判断与扣减，杜绝「查完再扣」之间的窗口
local stockKey = KEYS[1]
local orderKey = KEYS[2]
local userId   = ARGV[1]

-- 同一用户重复请求直接短路，不消耗库存
if redis.call('SISMEMBER', orderKey, userId) == 1 then
  return 2
end

local stock = tonumber(redis.call('GET', stockKey) or '-1')
if stock <= 0 then
  return 1   -- 已售罄
end

redis.call('DECR', stockKey)
redis.call('SADD', orderKey, userId)
return 0     -- 扣减成功
```
